## 2. Decisions

| # | Decision | Why |
| --- | --- | --- |
| D-1 | **Module shape.** `Features/Suspension`: `Contracts` (the two service interfaces, the DTOs, inputs and pages, `SuspensionErrorCodes`, `SuspensionApprovalRouting`, `Events`), the services, `SuspensionActivation`, `SuspensionMaintenance`, `SuspensionWorkflow`, `SuspensionEligibility`, `SuspensionGate`, `SuspensionAccess`, `SuspensionViews`, `SuspensionAudit`, `SuspensionServicePrincipal`, `EventHandlers/SuspensionApprovalOutcomeHandler` and the repository port. Entities in `Domain/Suspension`; repository, configurations and the worker in `Infrastructure` | ADR-003 §4.3 row 9 |
| D-2 | **Tables.** ERD §5.12 as `erd.dbml` gives them, column for column: `suspension_request` (one table for both types, `request_type` SUSPEND \| RESUME) and `active_suspension`, with indexes I-29, I-30, I-54 and the ERD's partial unique key `(project_id) WHERE ended_at IS NULL`. Beyond the ERD (F-8): `xmin` on both tables; the partial unique key `(project_id, request_type)` over the states that are not final; `(project_id, started_at, id)` for a project's history; CHECK constraints for the state facts (a DRAFT is never submitted; `effected_at` exactly while EFFECTED; past its requester a request has its effective date; a planned resumption belongs to a suspension and falls after its effective date; a period ends exactly when a resumption ends it, never before it started) | ERD §5.12 |
| D-3 | **The state machine** (§3) is the ERD's: ten edges in `SuspensionWorkflow`. The requester `submit`s (DRAFT, or RETURNED as the next revision, → SUBMITTED) and `withdraw`s (SUBMITTED, RETURNED → WITHDRAWN). **AHDA starts the review** (`start-review`, SUBMITTED → UNDER_REVIEW), which starts the WF-11 run in the same transaction, as WF-01 and WF-08 do. WF-11's outcome takes UNDER_REVIEW to APPROVED, RETURNED, REJECTED or WITHDRAWN. `activate` takes APPROVED to EFFECTED. The specification's APPROVED_PENDING_ACTIVATION is the ERD's APPROVED and its ACTIVATED the ERD's EFFECTED; its optional CANCELLED_BEFORE_ACTIVATION has no state in the ERD (F-5). REJECTED, WITHDRAWN and EFFECTED are final: any command is 409 `TERMINAL_STATE`; a step not in the machine 409 `INVALID_TRANSITION`. Fields change while DRAFT or RETURNED only (409 `SUSPENSION_NOT_EDITABLE`); only a DRAFT is deleted (HARD_DRAFT) | ERD §6 row 24; WF-09 §4.1, §4.3, Appendix A |
| D-4 | **Review through WF-11 (edges 23, 28).** `start-review` starts a run for the request's revision on routing key `SUSPENSION` or `RESUMPTION` — two routes, so AHDA can give each its own authority (TBC-SUS-002) — anchored on the project and its department, with the project's governance profile and no band or amount. **The run's requester is the originator**, whoever starts the review, so WF-11 keeps them from approving their own request (SUS-CC-07) and gives an external originator no authority (ADR-013, BR-SUS-037); they also withdraw it, which withdraws the request | TASK-035; WF-09 §4.4 step 4 |
| D-5 | **Approval completion and lifecycle activation are two distinct, separately auditable events — acceptance criterion 3.** `SuspensionApprovalOutcomeHandler` applies an outcome only to the revision under review while UNDER_REVIEW, otherwise audits it as ignored (EV-5); on APPROVED it sets the status and writes `Suspension.RequestApproved` by WF-11's last approver, **and calls no Project command**: the project is as it was, to the row version, and no suspension opens. The project moves only when the request is activated (D-6), a later transaction with its own events — `Suspension.RequestEffected` and Project's `Project.ProjectSuspended` or `Project.ProjectResumed` — by whoever activated it: WF-09's service principal (actor type `SERVICE`) or an AHDA user. No edge of the machine enters EFFECTED but from APPROVED, no WF-11 outcome leads to EFFECTED, and the database refuses APPROVED without the revision's APPROVED WF-11 run (D-11) | Acceptance criterion 3; WF-09 P3, DCL-SUS-01, DCL-SUS-02, BR-SUS-006, BR-SUS-036 |
| D-6 | **The activation, and edge 7.** `SuspensionActivation` is the one place a project's ACTIVE ↔ SUSPENDED transition is made. It revalidates, on the rows it reads: the effective date has come (409 `SUSPENSION_NOT_YET_EFFECTIVE`); the project is ACTIVE for a suspension, SUSPENDED for a resumption (422 `SUSPENSION_PROJECT_NOT_ELIGIBLE`, or 409 `SUSPENSION_ALREADY_EXISTS` for a suspension of a suspended project); a suspension has no open period yet, a resumption has one to end. It then stages, in one unit of work: the project's transition through **`IProjectSuspensionCommands`** — a command in Project's contracts, which Project implements by checking its own edge in `ProjectLifecycle` on the tracked row and staging its own audit event, as `IMilestoneAchievementRecorder` does for WF-05 — the period opened (`started_at`) or ended (`ended_at`, `resumption_request_id`), and the request EFFECTED (`effected_at`). One save commits them all or nothing (M-11, SUS-CC-09): a refusal stages nothing, so the request stays APPROVED and the project as it was (BR-SUS-021, BR-SUS-022), and the project's and request's row versions fail the save if either moved meanwhile (BR-SUS-034). The authority is the approved request, not a permission of a caller, so the command is not on `IProjectService` (`project-registration.md` §6). **Who activates**: `SuspensionActivationWorker` runs `SuspensionMaintenance` every `Suspension:Activation:PollInterval`, activating each APPROVED request whose effective date has come as the service principal `svc.suspension-activation`, each in its own unit of work (the specification's scheduled activation, DCL-SUS-03, SUS-CC-23); and `POST …/activate` lets AHDA activate one at once or retry (`SUSPENSION_ACTIVATE`, internal users). Both are safe to repeat: a second activation finds the request EFFECTED (409 `TERMINAL_STATE`), the pass finds nothing due | WF-09 §9.1, §9.2; edge 7 |
| D-7 | **Resumption triggers no rebaseline — acceptance criterion 2.** Suspension references no Schedule type: ADR-003 §8.2 has no Suspension → Schedule edge, and the architecture tests A-1 to A-6 refuse one. So neither suspension nor resumption can create a baseline, change the ACTIVE Approved Baseline or move a date (BR-SUS-008, BR-SUS-023, SUS-CC-12). While SUSPENDED, WF-03's own rule — a schedule is planned while its project is APPROVED_PLANNED or ACTIVE — refuses every schedule and baseline change, a rebaseline included (422 `SCHEDULE_PROJECT_NOT_ELIGIBLE`; DCL-SUS-05). Once resumed, a rebaseline is what it always is: WF-03's explicit candidate naming a WF-08 change authorisation (`change-request.md` D-9; BR-SUS-024, DCL-SUS-15); one without is refused 422 `SCHEDULE_CHANGE_AUTHORIZATION_REQUIRED` | Acceptance criterion 2; validation check 2; WF-09 P4, §9.3 |
| D-8 | **At most one active suspension per project — acceptance criterion 1 and the deliverable "ActiveSuspension singleton enforcement".** Raising a suspension request for a project that is SUSPENDED is refused 409 `SUSPENSION_ALREADY_EXISTS` (BR-SUS-003), and so is a second one while one is open — not REJECTED, WITHDRAWN or EFFECTED (BR-SUS-004); a second open resumption request is 409 `SUSPENSION_RESUMPTION_ALREADY_EXISTS` (BR-SUS-005). Each rule has one place, which holds it for any writer and however close together two requests arrive: the project's state, checked by the application and by the guard, which refuses a suspension request inserted for a project that is not ACTIVE and a resumption request for one that is not SUSPENDED; and two partial unique keys — `active_suspension (project_id) WHERE ended_at IS NULL`, the ERD's, and `suspension_request (project_id, request_type)` over the open states — whose violation the save answers with the 409 of the request's type. An application-side check for an open request, built first, gave no answer the key did not (§7.1 M-3) and was removed | Acceptance criterion 1; validation check 1; ERD F-041 |
| D-9 | **ADR-013: raise, not decide or activate.** Four permissions, group `SUSPENSION`: `SUSPENSION_VIEW`, `SUSPENSION_RAISE` (create, edit, delete a draft, submit, withdraw, either type), `SUSPENSION_REVIEW` (start-review), `SUSPENSION_ACTIVATE` (activate). Shipped: R04 view and raise at OWN — the projects the holder manages, internal or entity (WF-09 §3: the Project Manager prepares and submits; ADR-013: the entity fills in the information) — and R03 view and review at DEPT (§3: the Department Manager reviews). `SUSPENSION_ACTIVATE` ships to no role: §14 makes activation "System/service; no direct UI by default", which the worker is. Review and activation are refused to an external user whatever they hold — a check on the person, since R04 is held by internal and external users alike — and audited `Suspension.AuthorityRefused`, reason `EXTERNAL_USER`. Approval is WF-11's `APPROVAL_DECIDE` | ADR-013; WF-09 §3, §14 |
| D-10 | **When a project admits a request, and what a request needs** (`SuspensionEligibility`). A suspension is of an ACTIVE project, a resumption of a SUSPENDED one (BR-SUS-001, BR-SUS-002; ELG-SUS-003: no project in any other state); the project's state is read again by `submit`, `start-review` and `activate` (SUS-CC-03, ELG-SUS-004, ELG-RES-004), not by `withdraw`, so a request that can no longer take effect can still be taken back. Submission needs an effective date, not before today (the API's today, the UTC date; F-10) — 422 `SUSPENSION_INCOMPLETE`, `SUSPENSION_DATE_INVALID`. A planned resumption date is a suspension's, after its effective date, and planning information only (BR-SUS-031): nothing resumes on it | WF-09 §5.2 |
| D-11 | **The database holds the history and the criteria** (migration `TASK-062_GuardSuspensionHistory`). A request is born DRAFT at revision 1, never submitted, for a project its type admits; keeps its project, type and requester; moves only along the ten edges; raises its revision by one exactly when a RETURNED request is resubmitted; changes its fields only while DRAFT or RETURNED; is APPROVED only with the APPROVED WF-11 run of its revision; once final, nothing changes; only a DRAFT is deleted. A period is born open, keeps its project, request and start, ends once and never changes after; it is never deleted. **At commit** — deferred constraint triggers, so the order of one transaction's writes does not matter — a project is SUSPENDED exactly while it has an open active suspension; a period's requests are EFFECTED requests of its project, the suspension that opened it and the resumption that ended it; and an EFFECTED request has the period it opened or ended. So a project moved by a direct write, or a request effected without its period, is refused. No table is truncated. Migration `TASK-062_AddProjectSuspensionEdges` adds the two edges to `project.guard_project()` and changes nothing else of it | Acceptance criteria, for any writer |
| D-12 | **API shape (R-2 to R-5, R-21, R-47).** `/suspension-requests` with `projectId` required (R-3) and the filters `requestType` and `status` (sets), most recently changed first (P-2, I-29); each request carries the suspension period its effect opened or ended (`suspension`, null until EFFECTED). Commands on `/suspension-requests/{id}/…` answer with the request and honour `If-Match` when sent; `PUT` requires it. `/active-suspensions` with `projectId` required and the filter `open`, most recently started first: the project's suspension history across cycles (BR-SUS-039). A request the caller may not see is 404; one they may see but not act on, 403; a collection they may not see, an empty page. The specification's catalogue (§18) is mapped to these conventions and to WF-11's own endpoints (F-11) | api-conventions |
| D-13 | **Every change is audited** in the saving transaction (event-conventions §4 row 25), all with the request as subject and its type as an attribute: `RequestCreated`, `RequestChanged` (reason withheld), `RequestDeleted`, `OutcomeIgnored` (DATA_CHANGE); `RequestSubmitted`, `ReviewStarted` (with the run), `RequestApproved`, `RequestReturned`, `RequestRejected`, `RequestWithdrawn` (by WF-11's decider or the requester), `RequestEffected` (with the period and `effected_at`) (LIFECYCLE_TRANSITION); `AuthorityRefused` (AUTHORIZATION_DENIAL). Project audits its own two transitions, `ProjectSuspended` and `ProjectResumed`, naming the request (row 16) | event-conventions EV-9, EV-11; WF-09 SUS-CC-20, BR-SUS-036 |

## 3. The request state machine

| From | To | Command | Permission | Waits for | Writes |
| --- | --- | --- | --- | --- | --- |
| — | DRAFT | `POST /suspension-requests` | `SUSPENSION_RAISE` (entity PMs included) | SUSPEND: the project ACTIVE, no open suspension request. RESUME: the project SUSPENDED, no open resumption request | the request, revision 1 |
| DRAFT, RETURNED | SUBMITTED | `submit` | `SUSPENSION_RAISE` | the project's state as above; an effective date from today | `submitted_at`; from RETURNED, `revision_no` + 1 |
| SUBMITTED | UNDER_REVIEW | `start-review` | `SUSPENSION_REVIEW`, internal | an APPROVAL_AUTHORITY route for the type | a WF-11 run for the revision, the originator its requester |
| UNDER_REVIEW | APPROVED | WF-11 approves (edge 28) | WF-11's `APPROVAL_DECIDE` | every stage approved | nothing else: the project is unchanged |
| UNDER_REVIEW | RETURNED · REJECTED | WF-11 returns · rejects | as above | — | — |
| UNDER_REVIEW | WITHDRAWN | the originator withdraws the run | WF-11's | — | — |
| SUBMITTED, RETURNED | WITHDRAWN | `withdraw` | `SUSPENSION_RAISE` | — | — |
| APPROVED | EFFECTED | `activate`, or WF-09's pass as `svc.suspension-activation` | `SUSPENSION_ACTIVATE`, internal | the effective date has come; the project's state as above | `effected_at`; SUSPEND: the project SUSPENDED and a period opened; RESUME: the project ACTIVE and the period ended |

## 5. Error codes

`SuspensionErrorCodes` (R-27), beside the platform's `INVALID_TRANSITION`, `TERMINAL_STATE` and `CONFIGURATION_MISSING`:

| Code | Status | When |
| --- | --- | --- |
| `SUSPENSION_PROJECT_NOT_ELIGIBLE` | 422 | A suspension of a project that is not ACTIVE (nor SUSPENDED), a resumption of one that is not SUSPENDED — at raising, editing, submitting, review and activation |
| `SUSPENSION_ALREADY_EXISTS` | 409 | A suspension of a project already SUSPENDED, or a second open suspension request of the project |
| `SUSPENSION_RESUMPTION_ALREADY_EXISTS` | 409 | A second open resumption request of the project |
| `SUSPENSION_INCOMPLETE` | 422 | Submitting without an effective date |
| `SUSPENSION_DATE_INVALID` | 422 | An effective date before today on submission; a planned resumption date not after the effective date, or on a resumption |
| `SUSPENSION_NOT_EDITABLE` | 409 | Editing past DRAFT and RETURNED; deleting a request ever submitted |
| `SUSPENSION_UNDER_REVIEW` | 409 | `withdraw` under review: the originator withdraws the WF-11 run |
| `SUSPENSION_NOT_YET_EFFECTIVE` | 409 | `activate` before the effective date |

## 6. How other modules build on it

1. **TASK-064** builds SCR-108–110 on these 10 operations: approved and effected are the statuses APPROVED and EFFECTED, the active suspension is `GET /active-suspensions?projectId=&open=true`, and a resumption is a request of type RESUME on the same register. Impact, readiness and review tabs have no API yet (F-1). Built 2026-10-08: `suspension-closure-ui.md`.
2. **TASK-063** decides what completing or closing a suspended project does to its open requests and its open suspension (F-5) — built: `closure.md` D-6. The database ties SUSPENDED to an open active suspension only; ending the period as the project leaves SUSPENDED for a terminal state needs a WF-09 command, and its own end reason, which TASK-063 adds with its edges.
3. **TASK-065** guards D-8 in CI as its "single-ActiveSuspension enforcement" invariant; `SuspensionLifecycleTests.ASecondSuspensionRequestForAnAlreadySuspendedProjectIsRefused` and `SuspensionGuardTests` are the starting point.
4. **Other modules** read the project's state through `IProjectFactsReader` as before; each one's rule for a SUSPENDED project is its own (F-4). A module that needs to react to a suspension subscribes to nothing yet (F-6).
5. **Configuration**: an environment needs APPROVAL_AUTHORITY rows for `SUSPENSION` and `RESUMPTION` before a request can be reviewed (F-3).
