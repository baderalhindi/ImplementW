## 2. Decisions

| # | Decision | Why |
| --- | --- | --- |
| D-1 | **Module shape.** `Features/IntegrationMonitoring` with its `Contracts`, `EventHandlers` and internal services; entities in `Domain/IntegrationMonitoring`; the five tables of ERD §5.21 in `integration_monitoring`, as built (§3). Four migrations, one schema each (README R-7): `TASK-075_CreateIntegrationMonitoringTables`, `…_AddIntegrationMonitoringCrossModuleForeignKeys` (owner role, acknowledging user), `…_AddAuditForwardingInvocationForeignKey` (in `audit_activity`, closing TASK-033 F-3) and `…_GuardIntegrationMonitoringHistory`. FG-05 references only IdentityAccess's contracts (E-U1) and the producers' `Contracts/Events` (edges 31–33); `ModuleRegistry` is unchanged. | ADR-003 §4.3, §8.2; M-13. |
| D-2 | **Two kinds of invocation.** An attempt another module made is *observed*: it reaches FG-05 as telemetry, and its module keeps retrying it under its own policy. An attempt FG-05 makes is *executed* by its engine under the definition's policy. No module may reference IntegrationMonitoring (ADR-003 §8.2 has no edge into it), WF-15 already owns delivery, retry and redrive (FG-05 DC-INT-15: "FG-05 does not implement a second notification engine"), and IdentityAccess owns sign-in, so FG-05 executes only the operations it owns — today the directory reconciliation — and observes the rest. `invocation.source_module` says which: the producer, or `IntegrationMonitoring`. | ADR-003; FG-05 §7.2 (automatic retry by "integration runtime"), §10.3. |
| D-3 | **Telemetry through the outbox, after the producer committed.** IdentityAccess publishes `IdentityAccess.IntegrationInvocationCompleted` (event catalogue row 3, edges 31 and 33) and Notifications `Notifications.IntegrationInvocationCompleted` (row 4, edge 32), both carrying `IntegrationInvocationData`, whose fixed schema and the integration codes are in `Application/Common/Events` so no producer references FG-05. Notifications stages its event with the attempt's own record, carrying the intent's correlation id — the source request's. IdentityAccess's calls change nothing of its own, so it commits each event in a transaction of its own (`IOutbox.RecordAsync`, new) and **best effort**: if the event cannot be committed, the failure is logged and the sign-in goes on. The consumer stores each attempt under the event's id, so a repeated delivery stores nothing (EV-4), numbers it in its lineage, and applies it to the instance's health with the instance row locked. A message that breaks the contract (an unknown integration, a failure without its kind, a scheduled retry without its time) stays in the outbox with its error (EV-6). | EV-3, EV-4, EV-6; FG-05 §26 ("ingestion decoupled from core business transaction success"); the acceptance criterion: a failed invocation never changes business state — the producer's work committed before FG-05 saw anything. |
| D-4 | **What an identity provider call reports.** Decorators around the four adapters (`ObservedDirectoryService`, `…SingleSignOnProvider`, `…MultiFactorProvider`, `…IdentityVerificationProvider`) report each call: the provider unreachable or failing is a **technical** failure; a refused password, code or identity is a **business** failure — the provider answering; a refused service account is a **security** failure; a provider not configured was not called and reports nothing; an exception reports its type and is rethrown. The adapters know nothing of monitoring. | FG-05 §6.3, DC-INT-04; BR-INT-007. |
| D-5 | **Availability and freshness, two indicators.** Availability follows the latest technical outcome by completion time, whatever order attempts arrive in: DOWN when the latest technical failure is later than the latest success, UP otherwise, UNKNOWN before either. A business or security refusal leaves it alone. Freshness is the last success against the integration's configured window: FRESH within it, STALE after, UNKNOWN without a window — no window is configured by default (TBC-INT-12), so no threshold is invented. A pass re-evaluates freshness every 30 s, since it lapses without any new attempt. `evaluated_at` records the evaluation; it was `health_evaluated_at` in the ERD, renamed because only WF-02 and WF-03 may hold a column named for health (M-12, `OverallHealthAuthorityTests`). | Blueprint §17.1 ("Availability … distinct from freshness"); FG-05 §5, BR-INT-012 to -016; ERD derived register row 21. |
| D-6 | **The engine.** A lineage is one logical operation: instance, operation and idempotency key. Starting a lineage whose key already began one answers that lineage and runs nothing; two starts at once collide on the unique attempt number and the loser answers the winner's lineage. Each attempt is committed IN_PROGRESS before the operation runs, so a crash leaves evidence, then ends SUCCEEDED, RETRY_SCHEDULED (a technical failure before the last attempt; next attempt after `retry_backoff_seconds` × 2^(n−1)), DEAD_LETTER (a technical failure on the last attempt, or a security refusal at once) or FAILED (a business refusal, the source's to correct). The worker takes each due retry with its row locked (`FOR UPDATE SKIP LOCKED`), so two API instances never run the same retry; an attempt still IN_PROGRESS after `AbandonAfter` (1 h) lost its process and is ended as a technical failure, retried or dead-lettered like any other. Every attempt runs under the lineage's correlation id (D-14). | FG-05 §7.1–7.6, INT-CC-13/14/16, DC-INT-05/07; Blueprint §17.1. |
| D-7 | **A retry never rewrites the attempt it follows.** Each attempt is a row of its own. Once a lineage's next attempt exists, the attempt before it stops being its pending retry or its dead letter and becomes FAILED — what it failed with and when stay as they were. The database refuses every other change to an ended attempt, and any deletion (guard trigger). | INT-CC-13, BR-INT-024; keeps the retry queue and the set of current dead letters to live rows. |
| D-8 | **The directory reconciliation compares and never repairs.** For each active internal user linked to the directory, it reads the directory's job title, department reference and manager subject through IdentityAccess's new read contract `IDirectoryReconciliationSource` (E-U1), compares them with the platform's copy (`DirectoryComparison`: absent equals blank; a subject compares without case) and counts each person who differs, or whom the directory does not know. It applies nothing: those attributes are copied only at sign-in, by IdentityAccess (`sso-directory-integration.md` D-6). A mismatch raises one RECONCILIATION_MISMATCH alert, whose detail names people by user id and attributes by name — never a value, which is personal data. A directory that cannot be read ends the attempt as a technical failure (the run FAILED, or PARTIAL if some people were compared), which the engine retries. Each attempt is a `sync_run` of type RECONCILIATION with its counts (`records_applied` is always 0), and `IntegrationMonitoring.ReconciliationCompleted` is audited. An operator starts one with `POST /integration-reconciliations`; the request's `Idempotency-Key`, under the caller's id, is the lineage key, so a repeated request is the same run. | The acceptance criterion: "reconciliation mismatches raise an Operational Alert for investigation and never auto-repair authoritative data"; FG-05 §5.5, BR-INT-006, DC-INT-09. |
| D-9 | **Operational alerts.** AVAILABILITY when an integration goes DOWN (CRITICAL), DEAD_LETTER when a lineage is dead-lettered, RECONCILIATION_MISMATCH, FRESHNESS when it goes STALE, DELIVERY_RATE below the configured minimum (WARNING) — severities fixed until AHDA sets its own (TBC-INT-17). One alert stays live (OPEN or ACKNOWLEDGED) per instance and type, by a partial unique index and by every raise checking under the instance's lock, so an outage is one alert, not one per failed call. A disabled integration raises none. An operator acknowledges (who and when), then resolves or dismisses with a note (ADR-012); RESOLVED and DISMISSED are final. Recovery closes no alert and handling an alert changes no health: the integration recovering does not mean its dead letters or its data are dealt with. Raising is audited as `OperationalAlertRaised` by `svc.integration-monitoring`. | FG-05 §9.2, §10, BR-INT-033/036–039, DC-INT-10/11. |
| D-10 | **Integration health is kept apart from business state, in four places.** (1) FG-05 writes only `integration_monitoring`: `IIntegrationMonitoringRepository` maps no other table. (2) FG-05 reaches other modules only through their read contracts and events (`IntegrationHealthSeparationTests.Fg05ReachesOtherModulesOnlyThroughTheirReadContractsAndEvents`), so it has no command by which a failure could change a source record; and no code outside FG-05 can read an integration's health or alerts (`.NoModuleOutsideFg05ReachesIntegrationHealth`), so none can let it colour a business state. (3) Telemetry is read after its producer committed (D-3). (4) No column or property outside WF-02/WF-03 is named for health (D-5). The integration-failure simulation (§7.1) checks the result: every table outside `integration_monitoring`, the audit store and the outbox is digested before and after an outage and everything FG-05 does about it, and the digests are equal. | The acceptance criterion: "A failed integration invocation never silently changes a Project's or any business object's lifecycle state (verified by an integration-failure simulation test)"; BR-INT-001/002, DC-INT-01. |
| D-11 | **No payload, no secret, no message.** FG-05 stores no payload at all. An endpoint is named by its configuration key (`AD_LDAP_URL`), never its value. Telemetry's response code and error summary are kept only if they are plain codes (a type name such as `SocketException`, a code such as `UNREACHABLE`); anything else — a provider's text, which can echo an address or a token — is replaced by `[REDACTED]` before it is stored, and a business reference that is not `Type/id` is dropped. So R01 sees no payload by holding FG-05's grants: there is none to see (INT-CC-03). | FG-05 §8, INT-CC-07/08, BR-INT-017–020, SEC-INT-03/08/10. |
| D-12 | **Audit.** Every operator action and every system condition is integration audit, class INTEGRATION, so FG-06 lists it on ADM-053 for an `AUDIT_INTEGRATION_VIEW` holder: `OperationalAlertRaised`, `AlertAcknowledged`, `AlertResolved`, `AlertDismissed`, `InvocationRetried` (naming the lineage's correlation id), `ReconciliationRequested`, `ReconciliationCompleted`. Enabling and disabling are CONFIGURATION_CHANGE. None is business Activity (`ActivityTemplateCatalogue.ExcludedModules`). Attempts, runs and health are operational telemetry in FG-05's tables, not audit. | FG-05 §14.2, INT-CC-29, BR-INT-052; event catalogue row 31. |
| D-13 | **ADR-004's measures, over any window.** For an instance and a window: attempts and failed attempts (failure rate); operations that ended delivered or undelivered, leaving out those still being retried (delivery rate); the median and 95th-percentile attempt duration; and, from delivery receipts (`DELIVERY_RECEIPT` invocations in the send's lineage), the median time from a send's first attempt to its receipt. A measure over no sample is null, never 0 (Blueprint: missing ≠ zero). They are part of ADM-046's detail (`GET /integrations/{id}?from=&to=`, by default the last 24 h). A minimum delivery rate per integration code, when configured, is checked by the pass and raises DELIVERY_RATE. | ADR-004 participation amendment; FG-05 §5.1; TBC-INT-10. |
| D-14 | **Correlation end to end.** `CorrelationScope` (new, `Application/Common`) carries the work's correlation id with the asynchronous flow: the API sets it from `X-Correlation-Id` for each request, and the engine sets the lineage's own around every attempt, a worker's retry hours later included. The audit request context, the outbox envelopes, the invocations and every outbound HTTP call to the identity provider, the MFA provider, Nafath and the SIEM (`CorrelationPropagationHandler`, R-42) read it, so one search — `GET /integration-invocations?correlationId=` — returns a request's sign-in calls, its reconciliation's attempts and every directory read they made. | The acceptance criterion: "retries are idempotent and correlation-ID traceable end-to-end"; api-conventions R-41, R-42; CTL-29. |
| D-15 | **The registry.** Seeded (`db/seed`, §9): `DIRECTORY`, `SSO` (INBOUND), `MFA`, `NAFATH`, `EXCHANGE_EMAIL`, `SMS` (OUTBOUND), each ACTIVE with the ERD's policy (3 attempts, 60 s back-off) and one instance `PRIMARY`. The seed owns codes, direction and kind; labels, policy, owner role and activation are AHDA's once inserted, so a deployment never re-enables what an administrator disabled. An internal or future system is registered the same way (the test suite registers one). Each environment has its own database, so every instance in it is that environment's; the catalogue states the environment it describes (F-9). Activation is the definition's `status` (MOD-101, ERD lifecycle row 49): `POST /integrations/{id}/disable` stops alerts and FG-05's operations and changes no adapter; telemetry is still recorded (BR-INT-008). | Blueprint §17.1 (definition ≠ instance); FG-05 §4, §5.2, DC-INT-02. |
| D-16 | **Five permissions to R01 at ALL** (group `INTEGRATION_MONITORING`), by delivery-team decision as FG-04's and WF-15's: `INTEGRATION_VIEW` (catalogue, detail, alerts, runs), `INTEGRATION_LOG_VIEW` (attempts), `INTEGRATION_OPERATE` (retry, reconcile), `INTEGRATION_ALERT_MANAGE`, `INTEGRATION_CONFIGURE` (enable, disable; apart from operating, FG-05 §12.3). No other role, and never R08 (BR-INT-022). Integrations are platform-wide, so `[RequirePermission]` at the endpoint is the whole check. | FG-05 §12, §18; TBC-INT-19 (F-2). |
| D-17 | **Two service principals**: `svc.identity-integration` (`…00f4`) publishes IdentityAccess's telemetry; `svc.integration-monitoring` (`…00f3`) records telemetry, runs the engine and the pass, and raises alerts. | ERD D-2. |

## 3. The schema as built

ERD §5.21's five tables, with four additions and one rename, recorded in `erd.dbml` and `erd.md`:

| Table | As built |
| --- | --- |
| `integration_definition` | As the ERD. Row version (activation commands). CHECKs: `max_attempts ≥ 1`, `retry_backoff_seconds ≥ 0` |
| `integration_instance` | `health_evaluated_at` renamed `evaluated_at` (D-5). Row version; locked for every health change |
| `sync_run` | As the ERD. CHECKs: counts ≥ 0; `completed_at` set exactly when not RUNNING. Fixed once ended (guard) |
| `invocation` | **Added** `failure_category` (TECHNICAL · BUSINESS_VALIDATION · SECURITY; null exactly when SUCCEEDED or IN_PROGRESS) and `next_attempt_at` (set exactly when RETRY_SCHEDULED); **unique** `(integration_instance_id, operation_code, idempotency_key, attempt_no)`. Guard: changes only while IN_PROGRESS, except RETRY_SCHEDULED/DEAD_LETTER → FAILED (D-7) |
| `operational_alert` | **Added** `acknowledged_at` (with `acknowledged_by_user_id`); **partial unique** `(integration_instance_id, alert_type) WHERE status IN ('OPEN', 'ACKNOWLEDGED')`. Guard: born OPEN; what it reported never changes; forward only; RESOLVED and DISMISSED final and need a note |

No row of the schema is ever deleted (guard). Register indexes I-57 to I-60 (`indexing-strategy.md`); the retry queue is a partial index the worker owns.

## 5. API

All under `/api/v1`, tag `IntegrationMonitoring`, operation ids `IntegrationMonitoring_*`. Every non-2xx answer is the R-23 envelope; a sensitive write also answers 400 `IDEMPOTENCY_KEY_REQUIRED`/`…_INVALID`. 403 to anyone without the permission, R08 included.

| Operation | Permission | Answer |
| --- | --- | --- |
| `GET /integrations` | `INTEGRATION_VIEW` | 200 `IntegrationCatalogueView`: the environment, and every integration by code with its instances — availability, freshness, last success and failure, `evaluatedAt`, live alert count, the endpoint's configuration key |
| `GET /integrations/{id}?from=&to=` | `INTEGRATION_VIEW` | 200 `IntegrationDetail` with `ETag`: the definition, its retry policy, the operations FG-05 runs for it, and each instance's measures (D-13); 404 |
| `POST /integrations/{id}/enable`, `/disable` (sensitive; `If-Match` honoured) | `INTEGRATION_CONFIGURE` | 200 detail; 409 `INVALID_TRANSITION` (already so), `TERMINAL_STATE` (RETIRED); 412 |
| `GET /integration-invocations` (`integrationId`, `status` set, `operationCode`, `correlationId`, `idempotencyKey`, `sourceReference`, `startedFrom`/`To`; paged) | `INTEGRATION_LOG_VIEW` | 200 `InvocationPage`, newest first |
| `GET /integration-invocations/{id}` | `INTEGRATION_LOG_VIEW` | 200 `InvocationDetail`: the attempt, its lineage oldest first, and `retryPermitted`; 404 |
| `POST /integration-invocations/{id}/retry` (sensitive) | `INTEGRATION_OPERATE` | 200 detail of the new attempt; 409 `INVOCATION_ALREADY_SUCCEEDED`, `INVOCATION_NOT_RETRYABLE`; 422 `RETRY_NOT_PERMITTED` (an observed attempt: its module retries it), `INTEGRATION_DISABLED`; 404 |
| `POST /integration-reconciliations` `{integrationId}` (sensitive; its `Idempotency-Key` is the run's key) | `INTEGRATION_OPERATE` | 201 `InvocationDetail`, `Location` the attempt; 422 `RECONCILIATION_NOT_AVAILABLE`, `INTEGRATION_DISABLED`; 503 the source is not configured; 404 |
| `GET /sync-runs` (`integrationId`, `runType`, `status` sets, `correlationId`; paged), `GET /sync-runs/{id}` | `INTEGRATION_VIEW` | 200 runs with their counts |
| `GET /operational-alerts` (`integrationId`, `status`, `alertType` sets, `raisedFrom`/`To`; paged), `GET /operational-alerts/{id}` (`ETag`) | `INTEGRATION_VIEW` | 200 |
| `POST /operational-alerts/{id}/acknowledge`, `/resolve` `{note}`, `/dismiss` `{note}` (sensitive; `If-Match` honoured) | `INTEGRATION_ALERT_MANAGE` | 200; 400 without a note; 409 `INVALID_TRANSITION`, `TERMINAL_STATE`; 412 |

`GET /integrations` is one representation — a handful of rows and the environment — which the convention checker reads as an unpaged collection (C-9), recorded in `IntegrationMonitoringContractTests` as AuditActivity's access view is.
