| D-5 | **Revisions are immutable once submitted — acceptance criterion 2.** The responder drafts revision 1 of an ISSUED request and edits it while DRAFT (`PUT`, `If-Match` required); `submit` checks every required field and freezes it with the source version and state it was answered against. From then on no operation writes its values: there is no edit endpoint for a reviewer (`PUT` is `EXTERNAL_CONTRIBUTION_RESPOND`'s, which no AHDA role holds, and refuses anything but a DRAFT, 409 `CONTRIBUTION_NOT_EDITABLE`); the review's three decisions — `accept`, `return`, `reject` — write only the review's own columns and the status, and take no field value (the contract test checks their schemas). **A return produces a new revision**: it marks revision *n* RETURNED, as submitted, and opens revision *n*+1 as a DRAFT holding the same values, for the responder to correct and resubmit; a rejection ends the thread; an acceptance is final. Decisions are of the revision as a whole: no partial acceptance (BR-EXT-018). The database holds it for any writer (D-13) | Acceptance criterion 2; validation check 2; WF-13 §6, EXT-P-05, EXT-P-10 |
| D-6 | **Least-disclosure projection.** An external caller — any user who is not an active internal user — always gets the external projection: the same representation with every internal-only field null, named in `maskedFields`, and omitted on the wire by `[OmitMaskedFields]` (R-20(b), the mechanism FinancialKpi uses for ADR-010). Withheld from a request: the reviewer, who issued it, who wrote the row, the configuration version. Withheld from a revision: the source version and state, the reviewer, when review started, the internal note, who wrote the row. The review's reason is the entity's to read (EXT-F-127). Every property of the two representations is classified, external or internal-only, by a unit test that fails when a new property is added unclassified. A DRAFT request does not exist for an external caller (404, not listed). Source-application attempts are AHDA's only: an external caller lists none and reads none (404). The project appears as its Formal Project ID and the source record by its label (a task's title, WF-13 §8.2 "safe source label") | WF-13 §8.2, EXT-P-04, EXT-P-12, EXT-CC-05, EXT-CC-11; ADR-013 amendment: least disclosure governs internal-only and cross-entity material |
| D-7 | **ENTITY isolation — acceptance criterion 1.** A request is decided on its own anchors: its project, its project's department and Project Manager (owner), its responder and reviewer (assigned), and **the entity it is addressed to** — not the project's delivering entity, so two entities answering on one project are isolated from each other (WF-13 §8.3, EXT-P-14). The engine's rules then hold it (`authorization-engine.md` D-3): an external user reaches only records of their own entity, and a per-project assignment only its project, so R08's ENTITY grant on a per-project assignment is the "explicit ENTITY/Project grant". Single records out of scope answer 404 `NOT_FOUND`, identical to a nonexistent id (R-47): read, answer, edit, submit, and the revisions and attempts of another entity's request. Collections are filtered in SQL by the caller's `RecordScope` — the same clauses the engine decides a single record by — before paging and counting, so no filter, page or total betrays another entity's record (BR-EXT-034). A responder is an active external user of the addressed entity whose own grants let them answer the request once named on it; nothing is extended to make them eligible (BR-EXT-032). Ending the assignment ends access at once, and keeps the history (EXT-P-13) | Acceptance criterion 1; validation check 1; WF-13 §8.1, §8.3, EXT-CC-03, EXT-CC-21 |

| D-10 | **Source application — acceptance criterion 3.** An accepted revision of a typed source is ACCEPTED_PENDING_APPLICATION (acceptance is not application, EXT-P-07) until an AHDA holder of `EXTERNAL_CONTRIBUTION_APPLY` applies it: `POST /source-applications`. The schema names the adapter (`IExternalContributionTarget`, one per allowlisted source type); the adapter reaches the source only through its module's typed command — never a generic field write (EXT-P-17, M-3). `TaskProgressTarget` calls WF-04's `ITaskProgressContributions` (edge 19), which takes WF-04's project task lock, reads the task's row version afresh, and refuses — staging nothing — a task gone (FAILED `SOURCE_RECORD_NOT_FOUND`, terminal), cancelled (`SOURCE_RECORD_TERMINAL`, terminal), **changed since the answer was given** (CONFLICT, with the version found), of a project not ACTIVE (`PROJECT_STATE_NOT_PERMITTED`) or not taking a percentage now (`SOURCE_RECORD_STATE_INVALID`); otherwise it applies WF-04's own rule (ADR-009), rolls the Activity Execution Progress up and audits `TaskProgressReported` with the lineage. **Concurrency**: the version expected is the one the revision was answered against, or the one an AHDA user confirmed by `revalidate` after a CONFLICT — so a stale answer never overwrites a newer value blindly (EXT-P-09, BR-EXT-022), and nothing applies after a CONFLICT until it is revalidated (409 `SOURCE_APPLICATION_CONFLICT`); every attempt touches its revision, whose row version serialises attempts; WF-04's lock and the task's row version serialise against WF-04 writers. **Idempotency**: the caller's `Idempotency-Key` makes one attempt — a retry finds it and answers 201 with `Idempotent-Replayed: true`, applying nothing again (§20.4, Appendix C row 6); a revision has at most one APPLIED attempt, a partial unique key; an applied revision refuses another attempt (409 `SOURCE_APPLICATION_ALREADY_COMPLETED`). **Atomicity**: the attempt, the revision's status, the request's and WF-04's change commit in one transaction or not at all (EXT-CC-17). A terminal refusal ends the revision APPLICATION_FAILED and closes the request; a retryable one leaves it pending. Every attempt is recorded and returned 201, whatever its outcome, so a CONFLICT is a state, not an error (SCR-166). A **reference-only** answer is APPLIED on acceptance: there is no source | Acceptance criterion 3; WF-13 §7, §20.4, EXT-CC-13 to EXT-CC-18 |

Acceptance is not a formal approval (BR-EXT-014): no WF-11 run is started, and a source that needs one asks for it itself (§6.3) | WF-13 §6.3, EXT-CC-10, EXT-CC-12 |
| D-12 | **The project's lifecycle.** A request is drafted and issued while the project is APPROVED_PLANNED, ACTIVE or SUSPENDED (§11.1; 422 `PROJECT_STATE_NOT_PERMITTED`): not before approval, and not once COMPLETED — the closeout contributions WF-13 allows then have no schema yet — or CLOSED. Every write to a CLOSED project's records is refused 409 `PROJECT_CLOSED` (`ClosedProjectGuard`, TASK-063; BR-EXT-039); reads go on. A task's percentage applies only while the project is ACTIVE, WF-04's own rule | WF-13 §11.1, DCL-EXT-16 |
| D-13 | **The database holds the history and the criteria** (migration `TASK-066_GuardExternalParticipationHistory`). A request is born a DRAFT of AHDA's for a project that admits one, keeps its project, entity and origin, moves only along its seven edges, keeps its purpose, source, due date and issue once issued, answers to an EXTERNAL user of its own entity and is reviewed by an INTERNAL user, and changes no more once final; only a DRAFT is deleted. A revision is born a DRAFT of an open request with its project and entity, numbered one after the RETURNED revision it corrects; is contributed by an EXTERNAL user of its entity and reviewed by an INTERNAL one; moves only along its eight edges; once submitted keeps who submitted it, when, and against which source version; is decided once; changes no more once final; is never deleted. **A revision's values are written only while it is a DRAFT of a request that is not final.** An attempt is never deleted and never changed but by the one revalidation of a CONFLICT. At commit (deferred constraint triggers): a request has at most one revision that is not final and its status agrees with its revisions; an attempt is of an accepted revision; a revision of a source is APPLIED only with its APPLIED attempt and APPLICATION_FAILED only with a FAILED one. No table is truncated | Acceptance criteria 2 and 3, for any writer; WF-13 BR-EXT-048 |

## 3. State machines

**Request**

| From | To | Command | Permission | Waits for |
| --- | --- | --- | --- | --- |
| — | DRAFT | `POST /external-update-requests` | `EXTERNAL_REQUEST_MANAGE`, internal | the project APPROVED_PLANNED, ACTIVE or SUSPENDED; an ACTIVE entity; a typed schema; the source record of the project; the people, when named, eligible |
| DRAFT | ISSUED | `issue` | as above | all of the above again; responder and reviewer named; the due date not past; PARTICIPATION enables the type for the project's mode |
| ISSUED | IN_PROGRESS | the responder drafts revision 1 | `EXTERNAL_CONTRIBUTION_RESPOND`, the responder | — |
| IN_PROGRESS | RESPONDED | the revision is submitted | as above | required fields; the source record still the project's |
| RESPONDED | IN_PROGRESS | the revision is returned | `EXTERNAL_CONTRIBUTION_REVIEW`, the reviewer | — |
| RESPONDED | CLOSED | rejected; accepted reference-only; applied; or its application failed terminally | review or apply | — |
| ISSUED, IN_PROGRESS | CANCELLED | `cancel {reason}` | `EXTERNAL_REQUEST_MANAGE`, internal | — |

**Revision**

| From | To | Command | Permission |
| --- | --- | --- | --- |
| — | DRAFT | `POST /external-contributions` (revision 1); a return (revision *n*+1, with the returned values) | the responder; the reviewer's return |
| DRAFT | SUBMITTED | `submit` | the responder |
| SUBMITTED | UNDER_REVIEW | `start-review` | the reviewer, internal |
| UNDER_REVIEW | RETURNED · REJECTED | `return {reason}` · `reject {reason}` | as above |
| UNDER_REVIEW | ACCEPTED_PENDING_APPLICATION · APPLIED | `accept {internalNote?}`: pending for a typed source, applied for reference-only | as above |
| ACCEPTED_PENDING_APPLICATION | APPLIED · APPLICATION_FAILED | an attempt applies it, or finds the source gone or terminal | `EXTERNAL_CONTRIBUTION_APPLY`, internal |

**Application attempt**: APPLIED, CONFLICT or FAILED as made; a CONFLICT may be revalidated once (`revalidate`), which the next attempt then expects. The ERD's PENDING, REVALIDATING and RETRY_SCHEDULED belong to an asynchronous attempt and are not entered (F-7).

## 4. Endpoints

## 6. How other modules build on it

1. **TASK-067** builds SCR-160 to SCR-167 on these 22 operations (`external-participation-ui.md`). The same `GET` serves both views: an external caller's payload lacks the internal-only fields and names them in `maskedFields` — TASK-067's criterion compares the two payloads. A CONFLICT is an attempt's status with the version found, not an error, and `revalidate` is its resolution; `responseFields` on a request is the form to render. SCR-167 (monitor), evidence, comments and reminders have no API yet (F-1).
2. **TASK-068** (Nafath) gives external users their sign-in; WF-13 needs nothing more of it: a user's access is their FG-03 assignment, checked on every request.
3. **A new source adapter** is a command in its module's contracts in the shape of `ITaskProgressContributions` — read with a version token; stage under the module's own lock and rules in the caller's unit of work; audit with the lineage — an `IExternalContributionTarget` here, a schema in `ContributionSchemas`, a row in ADR-003 §8.2 edge 19 and `ModuleRegistry`, and a CONTRIBUTION_TYPE item AHDA publishes (F-4).
4. **FG-03**: per-project R08 assignments of the entity's contributors, possibly of entities other than the project's delivering one (§8.3), are what makes them eligible responders. **FG-04**: the CONTRIBUTION_TYPE items and a PARTICIPATION version (F-3).
5. **FG-01/FG-02** have no projection to read yet (F-1).
