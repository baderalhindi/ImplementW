## 2. Decisions

| # | Decision | Why |
| --- | --- | --- |
| D-1 | **Where it lives.** AHDA's screens under `/external-requests` (index SCR-160, `new?projectId=` and `:id/edit` SCR-161, `applications` SCR-166, `monitor` SCR-167) and `/external-contributions/:id` (SCR-165); the entity's lists at `/my-external-requests` (SCR-163) and `/my-contributions` (SCR-164); **SCR-162 is one address for both audiences**, `/external-requests/:id`. A project's requests are the workspace tab **External requests** (`/projects/:id/external-requests`, audience `reached`), after Closeout. The sidebar group shows AHDA the register and both monitors, an entity user its own requests and contributions — never both. SCR-161 starts from the workspace tab, as SCR-106 does; it and the detail work without reading the project (403 and 404 alike, `change-request-ui.md` D-1). The Step 16 `/views/scr-16x/…` routes are proposals only | ADR-002; WF-13 §12.2 |
| D-2 | **Acceptance criterion 1: least disclosure by projection, on the screen too.** The layout of SCR-162 follows the record's own `projection`, which the API decides — never the session's user type. Every page renders what `disclosedRequest` / `disclosedContribution` (`projection.ts`) return: the record without each field it names in `maskedFields` and, for an EXTERNAL record, without every field AHDA classifies internal-only — the lists of `ExternalParticipationViews` (request: reviewer, issuer, configuration version, authors; revision: source version and state, reviewer, review start, internal note, authors). So a field the server should have withheld still never reaches an external page. The external view has no AHDA handling section, no internal note, no source version, no application lineage, and **reads nothing internal**: no `/source-applications`, no reviewer's `/users/{id}`, no `/external-entities`. An entity reads every accepted outcome as *Accepted* (`externalOutcomeOf`): AHDA's application is not theirs to see (§9.3; attempts are AHDA's only, TASK-066 D-6). AHDA's screens (SCR-160, -161, -165, -166, -167) are wrapped in `InternalOnly`: an entity user who reaches one by address is pointed to their own list and the screen makes no read at all. A rule test classifies every field of both representations, external or internal-only, and fails on a new unclassified one | Acceptance criterion 1; workbook check 1; WF-13 §8.2, EXT-P-04 |
| D-3 | **Gate decision: no origination, no escalation.** An entity user is offered no *Create request*, issue, edit, delete, cancel, reassignment, review decision, apply or revalidate, whatever role they hold (R04 is employer-neutral, ADR-013) — on SCR-162, SCR-163, SCR-164 and the workspace tab; nothing in WF-13's screens escalates for anyone. Their only write is the answer to a request naming them as responder | Gate decision (19 Sep 2026); TASK-066 D-3, D-9 |
| D-4 | **Acceptance criterion 2: conflict and retry are states, not errors.** An apply answers 201 whatever its outcome (TASK-066 D-10), so SCR-166 derives each accepted answer's state from its status and newest attempt (`applicationStateOf`): **Pending application**; **Conflict: revalidation needed** (the source changed since the answer; the card names the version answered against and the version found; action *Revalidate*); **Revalidated: apply again**; **Not applied: can retry** (a refusal the source may lift — project not active, task not taking a percentage; action *Apply again*); **Applied**; **Failed: cannot be applied** (source gone or cancelled; no action). Each has its own words, mark (diverging arrows, circular arrow, cross…), badge style and card edge — a conflict amber and outlined, a retry blue and dashed, a failure red — and a legend explains them. An attempt's outcome is told in a notice of its own (a CONFLICT is a warning naming the conflict), never an error alert; a 409 `SOURCE_APPLICATION_CONFLICT` re-reads the list. Cards needing action come first; each keeps its full lineage (attempt, outcome, versions expected and found, safe refusal, who, revalidation, correlation id) | Acceptance criterion 2; workbook check 2; WF-13 §12.3 SCR-166, §7.3–§7.4 |
| D-5 | **Idempotent apply.** `ApplyDialog` makes the attempt's Idempotency-Key once per dialog: sent again after a lost answer, the API replays the same attempt (`Idempotent-Replayed`) and nothing is applied twice. No other command is retried (TASK-066 F-11) | TASK-066 D-10, §20.4 |
| D-6 | **ADR-013 core rewrite: a working workspace, not only an inbox.** The entity's Project Manager and contributors work in the project workspace they already have (Path A on their own tasks, TASK-066 D-3) and find AHDA's requests there, on the External requests tab, beside SCR-163/164. The tab shows AHDA every request on the project with *Create request* while the project takes them (APPROVED_PLANNED, ACTIVE, SUSPENDED; never on a CLOSED project — the closed-workspace sweep covers the tab); it shows an entity user its own entity's requests, read-only | ADR-013 amendment |
| D-7 | **ADR-019: nothing further for entity users.** No WF-13 screen composes a report, saves a view or exports, for either audience; filters live in the address only. The Project Dashboard ADR-019 grants is FG-01's and not built (F-5) | ADR-019 |
| D-8 | **The answer (SCR-162 external).** One input per field of the request's typed schema (`responseFields`) and nothing else: a number with its range and at most four decimals, a date, a narrative tagged with the language it is typed in. A draft may be incomplete; *Submit response* checks every required field first, then asks for confirmation — a submitted answer cannot change — and saves and submits. The API's refusals name `fields[i].value` by the index sent; `responseIssuesOf` maps them back to the field. After a return, the next revision's draft opens with AHDA's reason above it. Only the named responder sees the form; anyone else of the entity reads why not | TASK-066 D-5, D-8 |
| D-9 | **Review (SCR-165): decide, never edit.** The submitted values are shown read-only beside the source as it stands now (WF-04's task percentage) and the revision this one corrects; the page has no input. The source's row version now (its ETag, R-21) is compared with the version the answer was given against: a change is a warning that applying will record a conflict, not a refusal. Only the request's assigned AHDA reviewer is offered *Start review*, then *Accept* (internal note), *Return for correction* or *Reject* (reason the entity reads, required, and internal note); the bodies carry words only. Anyone else is told who decides | TASK-066 D-5, D-11 |
| D-10 | **SCR-161 with what the person may read.** The contribution type from the CONTRIBUTION_TYPE catalogue (its code decides whether a task is named), the entity from the organisation, the task from the project's live leaf tasks, the responder and reviewer by search — each offered as a list when readable and as an id otherwise (MASTER_DATA_VIEW, ORGANIZATION_VIEW and USER_VIEW ship to R01 only, F-2). Defaults: the project's delivering entity, the drafting AHDA user as reviewer. *Save draft* (people and due date may wait) or *Save and issue* (both people and a due date not before today); a refused issue leaves the saved draft in the form with the refusal on its fields | TASK-066 §3, D-12 |
| D-11 | **Reads.** Revisions and attempts are listed per parent (`externalUpdateRequestId`, `externalContributionId` required, TASK-066 D-14), so SCR-164 reads the entity's requests, then each one's revisions; SCR-166 reads requests RESPONDED or CLOSED of a typed source, then their accepted revisions, then each one's attempts — six at a time (`readInBatches`). Lists are most recently changed first, filtered in the address (status, due condition, "mine"); SCR-167 counts, per project and entity, the requests the API lists to the person (not started, being drafted, with AHDA, due/overdue, responders named, AHDA drafts, closed/cancelled) and says that access expiry is not available | TASK-066 D-14; WF-13 §12.3 |
