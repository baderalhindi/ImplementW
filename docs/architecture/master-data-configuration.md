## 2. Decisions

| # | Decision | Why |
| --- | --- | --- |
| D-1 | **One governed lifecycle primitive in `Application/Common/Governance`.** `GovernedLifecycle` holds the four steps over any `GovernedEntity`: `CheckDraftEdit`, `CheckValidate`/`Validate`, `CheckPublish`/`Publish`, `Retire`, each answering `Applied`, `InvalidTransition`, `TerminalState` or `SeparationOfDuties`. Master data items, KPI definitions and configuration versions use it; TASK-110 uses it for permission profile versions. | ERD D-12 ("one primitive in `Application/Common` (M-10), used by five modules, per TASK-034 and TASK-110"); `solution-architecture.md` §11.3 places the profile in IdentityAccess and the primitive here, which is how the ADR-018 amendment is met. |
| D-2 | **Three people, and the draft is the author's.** The author is the row's creator and the only person who edits it while DRAFT. The reviewer who validates it is someone else; the publisher is neither of them. A VALIDATED row is not edited: it is published or retired, and a change is a new row or version. RETIRED is terminal. | ERD D-12: "Author, reviewer and publisher must differ." If anyone could edit a draft, the reviewer could validate their own edits. The seeded `RISK_MATRIX` draft is authored by `svc.platform-seed`, so it is completed in a version created from it (D-4). |
| D-3 | **Master data is identity, not versioned.** An item's catalogue and code never change; its parent is in the same catalogue, only where the catalogue allows a hierarchy, and never below itself. A PUBLISHED item takes a label, description or order correction as an audited edit by any administrator; its parent is fixed (`…_PUBLISHED_IMMUTABLE`). A child is published only under a PUBLISHED parent. A shipped (`is_system`) item is never retired (`…_SYSTEM_ROW`). Retiring an item stops new use; rows that reference it keep it. Catalogues are the platform's: only the name is edited. A KPI definition's unit is a PUBLISHED `KPI_UNIT` item; once PUBLISHED its unit and direction are fixed. | ERD §5.3: master data is "retired, never deleted, and never versioned — a label correction is an audited edit". A catalogue AHDA created would be referenced by no column (seed D-7). A KPI's unit and direction are what its recorded values mean. |
| D-4 | **A version's content is one document, replaced whole while DRAFT.** `ConfigurationContent` has one section per typed table (or table group) of ERD §5.3; each family carries only its sections (`ConfigurationSections`), and scalar `values` are open to all. `PUT /configuration-versions/{id}` replaces the change summary and the whole content. A new version may start as a copy of any version of its family (`basedOnVersionId`); the source is read, never changed. Content is checked on every write (well formed, in range, unique, and referencing a PUBLISHED item of the right catalogue, a PUBLISHED KPI definition or an existing role) and again at validation and publication, with the completeness rules of D-14/D-15 added; an empty version is never validated. Every issue is reported at once by path (`content.riskMatrixCells[3].ratingCode`), never by value. | A version is the unit of publication (ERD §5.3), so it is written as a unit. Checking again at each step catches an item retired since the draft was written. Copying is how a change is made without touching history. |
| D-5 | **Resolution is by date alone, and never guesses.** Of a family's versions that were ever published and not withdrawn before taking effect, the one with the latest effective-from at or before the moment is chosen; if that one was withdrawn by then, nothing is effective — an earlier version is never brought back. Two versions claiming the same moment is ambiguity, and resolution refuses to pick. A record that must not follow later publications pins the version id it used and resolves it with `ResolvePinnedAsync` (ERD D-13). Nothing is cached: a publication applies from its effective moment. The derived effectivity shown on a version is FUTURE_EFFECTIVE, ACTIVE, SUPERSEDED or RETIRED. | Acceptance criterion 2. ERD D-13 ("resolve the values effective at the transaction date"; effectivity "derived … not stored"). Bringing back a superseded version after a withdrawal would apply configuration nobody decided to apply. |
| D-6 | **Publishing never touches another version.** A publication takes effect now or later, never in the past, and after every earlier publication of the family (`…_EFFECTIVE_FROM_INVALID`). Supersession is derived, so the prior version's row is not written. `effective_to` is written only by a version's own retirement: now, or its effective-from if it has not taken effect (withdrawn before effect). `ConfigurationVersion.EffectiveTo`'s comment said it was set when the next version took effect; it is corrected. | Acceptance criterion 1. A backdated version would change what a past transaction resolves to; an effective-from before an earlier publication would reorder history. Writing `effective_to` on the predecessor at each publication would be a rewrite of a published row. |
| D-7 | **The database enforces the history, whoever writes.** Migration `TASK-034_GuardConfigurationHistory`: trigger `guard_configuration_version` refuses any change to a PUBLISHED version except its own retirement, any change to a RETIRED one, and the deletion of anything but a DRAFT (SQLSTATE 23001); on publication it locks the family row and refuses an effective-from not after every earlier publication (23514, constraint `ck_configuration_version_effective_from_order`, answered 422). Trigger `guard_configuration_content` on all 17 typed tables refuses any write to the rows of a version that is not DRAFT. CHECK `ck_configuration_version_effective_from` (effective-from exactly when published) and `ck_configuration_version_effective_to` (not before effective-from). The migration also maps `xmin` as the row version of catalogue, item, KPI definition and version (no DDL, as TASK-031). | The acceptance criterion is about the data, not only the API: a script, a seed or a later module could otherwise rewrite history. The family lock makes two concurrent publications serialise instead of interleaving. |
| D-8 | **Missing configuration fails the operation explicitly.** `IConfigurationResolver` throws `ConfigurationMissingException` (reason `UnknownCode`, `NoEffectiveVersion`, `AmbiguousVersions`, `VersionNotPublished`, `EntryMissing`, `EntryInvalid`, `ItemUnavailable`); the API's exception handler answers it 422 `CONFIGURATION_MISSING` (api-conventions §4.4). `ResolvedConfiguration` offers only `Require…` accessors — `RequireInteger`, `RequireDurationDays`, `RequireDecimal`, `RequirePercent`, `RequireBoolean`, `RequireText`, `RequireGovernanceProfile`, `RequireMaterialityBands` (all three or none), `RequireRiskRating`, `RequireNotificationEventFamily`, `IsContributionEnabled`, `RequireKpiPolicy` — each of which throws rather than default. A value read as another type is invalid, not converted; a contribution type with no rule is not "disabled". | Acceptance criterion 3; Blueprint Section 12 ("fails closed on critical ambiguity or missing configuration"). The message names the family and entry, never a value. |
| D-9 | **Modules use master data through `IMasterDataResolver`.** `RequirePublishedItemAsync(catalogue, id)` accepts only a PUBLISHED item of that catalogue; `ListPublishedItemsAsync` gives a form its values in display order. | E-U2 covers "resolved master data" as well as configuration. |
| D-10 | **Four permissions, R01 at ALL, and no record scope.** `MASTER_DATA_VIEW`, `MASTER_DATA_MANAGE` (catalogues, items, KPI definitions) and `CONFIGURATION_VIEW`, `CONFIGURATION_MANAGE` (families, versions, resolution), group `MASTER_DATA_CONFIG`; the two `_MANAGE` are `is_privileged`. Added to `PermissionCatalogue` and the seed together. Master data and configuration are platform-wide, so the endpoint's permission is the whole check, as for roles (`identity-access-administration.md` D-9). | No controlled source fixes ADM-020–029 to a role; the user decided on 2026-09-28 to ship them to R01 as a delivery-team decision, recorded as F-1. Separation of duties needs three R01 holders. |
| D-11 | **Step-up on the two operations that change what the platform applies**: `MasterDataConfig_PublishConfigurationVersion` and `MasterDataConfig_RetireConfigurationVersion` in `Identity:StepUp:Operations`. | ADR-010; the list is configuration (TASK-029 D-5). |
| D-12 | **Every change is a CONFIGURATION_CHANGE audit event**, staged with the change through `IAuditTrail` (TASK-033): 16 event types (event-conventions row 12). An item's or KPI's fields are audited as before/after values; a version's content as the SHA-256 of its canonical JSON before and after, with each section's row count. | A PUBLISHED version keeps its content in full, so the audit store need not copy configuration. See F-9 for drafts. |
| D-13 | **The API conventions, including R-4.** No `PATCH`, no `DELETE` (every FG-04 table is RETAIN or CASCADE under a RETAIN parent). `PUT` requires `If-Match` (428/412); commands honour it when sent; every `POST` and `PUT` is a sensitive write needing a uuid `Idempotency-Key`. The content is part of the version's representation (`GET`/`PUT /configuration-versions/{id}`) and resolution is its own resource keyed by the family code (`GET /configuration-resolutions/{familyCode}?asOf=`), because R-4 allows only a POST command after `{id}`: the first build's `…/{id}/content` and `…/{code}/resolution` failed `contract-check.py` C-2 and were moved. Module codes are `MASTER_DATA_CONFIG_*`. | `api-conventions.md` R-4, R-5, R-21, R-23, R-27, R-35, R-36. |
| D-14 | **ADR-011 and ADR-012; the schema is published and the values are not seeded.** RISK_MATRIX validates only with five probability levels, five levels for every PUBLISHED `IMPACT_DIMENSION` item (cost, schedule, reputation, operational — shared by risks and issues), at least one rating and all 25 cells, each naming a rating of the same version. Every label in every family is a `BilingualLabel` (both languages, R-17); requests check both. Nothing beyond TASK-027's generic DRAFT risk scale is seeded: AHDA completes it in a version 2 created from it. | Gate decision. OQ-005 and OQ-006 hold the values; §5 criterion 2 shows the seeded scale refused as incomplete, then completed and published. |
| D-15 | **The participation amendments as published configuration.** ADR-013: PARTICIPATION holds a rule per participation mode (ENTITY_MANAGED, AHDA_MANAGED — the project's mode is its own column, set by TASK-041) and `CONTRIBUTION_TYPE`; it validates only with a rule for every PUBLISHED contribution type in both modes. ADR-004: NOTIFICATION_ROUTING holds, per event family, Mandatory/User-configurable, its channels (IN_APP, EMAIL, SMS) and its recipient roles; a Mandatory family must reach at least one role on at least one channel enabled by default, so the SMS event set is configuration. ADR-015/016: GOVERNANCE_PROFILE validates only with settings for every PUBLISHED profile (1–3 change bands); MATERIALITY_BAND only with bands 1, 2 and 3 for every profile; APPROVAL_AUTHORITY rows name existing roles and bands 1–3. | Workbook participation amendments. ADR-013's "no external approval authority" is a property of the deciding user, not of a role (R04 is held by internal and external users), so it is TASK-035's check at decision time (F-13). |
| D-16 | **The authorization engine picks the FIELD_CLASSIFICATION version by D-5.** `AuthorizationRepository.GetFieldClassificationsAsync` used "latest PUBLISHED version effective now", which would bring back an older version after the current one was retired. It now applies D-5's rule. | One resolution rule on the platform. The engine still reads the table itself rather than through `IConfigurationResolver` (F-6). |
| D-17 | **Shared code, not copied.** `IdentityAccessControllerBase` is renamed `AdministrationControllerBase` and used by both modules; FG-04 reuses IdentityAccess's `AdministrationResult`, `AdministrationError`, `FieldIssue`, `Versioned` and `PageRequest` through its contracts (E-U1), and `AdministrationPersistence.ExpectVersion`/`ContainsPattern`. `IRoleDirectory` is added to the IdentityAccess contracts so FG-04 can check the roles its matrices name. | DRY within ADR-003's edges: MasterDataConfig → IdentityAccess is E-U1. `SaveResult` stays per module because IdentityAccess's is not in its contracts. |

## 4. Error codes

`MasterDataConfigErrorCodes` (R-27). `errors[]` names each field or content path with a code: the shared `REQUIRED`, `NOT_FOUND`, `INACTIVE`, `DUPLICATE`, `NOT_ALLOWED`, and `ContentIssueCodes` `SECTION_NOT_ALLOWED`, `WRONG_CATALOGUE`, `NOT_PUBLISHED`, `OUT_OF_RANGE`, `MALFORMED`, `INCOMPLETE`.

| Code | Status | When |
| --- | --- | --- |
| `MASTER_DATA_CONFIG_DUPLICATE_KEY` | 409 | An item code within its catalogue, a KPI code, or a version number another request took first |
| `MASTER_DATA_CONFIG_REFERENCE_INVALID` | 422 | A catalogue, parent, unit, family or source version that does not exist or may not be used |
| `MASTER_DATA_CONFIG_SEPARATION_OF_DUTIES` | 422 | D-2 |
| `MASTER_DATA_CONFIG_PUBLISHED_IMMUTABLE` | 422 | An item's parent, or a KPI's unit or direction, changed once PUBLISHED |
| `MASTER_DATA_CONFIG_SYSTEM_ROW` | 422 | A shipped item retired |
| `MASTER_DATA_CONFIG_CONTENT_INVALID` | 422 | D-4's entry rules |
| `MASTER_DATA_CONFIG_CONTENT_INCOMPLETE` | 422 | D-14/D-15 completeness, or empty content, at validation or publication |
| `MASTER_DATA_CONFIG_EFFECTIVE_FROM_INVALID` | 422 | D-6; also when a concurrent publication committed first (D-7) |
| `CONFIGURATION_MISSING` (platform) | 422 | D-8, from any operation that resolves configuration |
