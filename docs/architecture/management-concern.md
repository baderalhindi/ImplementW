| D-3 | **The state machine** (§3) is the row's and the ERD's: six edges in `ConcernWorkflow`. `assign`: OPEN → ASSIGNED, a reassignment keeps ASSIGNED or IN_PROGRESS. `start`: ASSIGNED → IN_PROGRESS. `submit-resolution`: IN_PROGRESS → PENDING_VALIDATION. WF-11's approval: → RESOLVED; its return, rejection or withdrawal: → IN_PROGRESS as the next revision, the resolution kept for correction — the specification has no terminal rejection of a resolution (§5.6). `close`: RESOLVED → CLOSED. `assess` and `review` keep the state. Fields and impacts change until the resolution goes to validation (409 `CONCERN_NOT_EDITABLE`); a CLOSED concern takes no command (409 `CONCERN_CLOSED`); any other step is 409 `INVALID_TRANSITION`. An issue and a challenge share it (ISS-GP-01); the type is fixed when the concern is raised | Row: "Open to Assigned to In Progress to Pending Validation to Resolved to Closed"; the specification's own lifecycle differs (F-1) |
| D-4 | **Severity, the acceptance criterion: computed from documented rules, never input.** `ConcernSeverity`: (1) the impacts fit the scale of the RISK_MATRIX version in force — the dimension set and levels risks and issues share (ADR-011) — each dimension at most once, defined by the version, at a level it defines; a dimension not given does not apply (VAL-ISS-006), so unlike a risk an issue need not assess every dimension; every miss is a field issue, 422 `CONCERN_IMPACT_INVALID`; (2) the overall impact is the highest level among them (BR-ISS-008); (3) the severity is the CONCERN_SEVERITY item whose code the same version names in its value `CONCERN_SEVERITY_LEVEL_{n}` for that level, and the item must be PUBLISHED (BR-ISS-009); (4) the concern stores the overall level, the severity item and the version id (`severity_configuration_version_id`, ERD §7 row 13), so a later publication changes no recorded severity, and the next assessment is computed under, and pins, the version in force then. Generic (OQ-006): no level, dimension, code or label is named in code. No version, no mapping for the level, or an unpublished item fails closed: 422 `CONFIGURATION_MISSING`. **Never input**: no request model has a severity field, an unknown property is ignored (as everywhere in the API), so a client's severity is dropped and the computed one stored; and from PENDING_VALIDATION the database refuses any change to it (D-12). A concern raised without impacts has no severity until it is assessed | Acceptance criterion 1; WF-07 §5.1, §12.3 |
| D-5 | **Priority is separate.** A PUBLISHED PRIORITY item (422 `CONCERN_PRIORITY_INVALID`), chosen by people on raise and edit. Severity never sets it and it never sets severity (BR-ISS-011). No minimum-priority rule and no recommendation: their values are TBC-ISS-004 (F-10) | Row: "Severity distinct from user-set Priority" |
| D-6 | **Escalation, the acceptance criterion: one NotificationIntent per escalation event.** An escalation is a `concern_escalation` row, numbered within its concern, an overlay that never changes the concern's status (ISS-GP-06). It is addressed to the role WORKFLOW_POLICY's `CONCERN_ESCALATION_ROLE` (TEXT, a role code) names when it is raised; no value, or an unknown role, fails closed (422 `CONFIGURATION_MISSING`). Its intent, `ManagementConcern.ConcernEscalated` (family `CONCERN_ESCALATION`, deep link `/projects/{p}/issues-challenges/{c}`, parameters `concernType`, `escalationNo`, `escalatedToRoleCode`, `severity`, no free text), is staged in the outbox in the transaction that writes the row, with the escalation's id as idempotency key and source reference. Exactly once is held at three layers: **(a) the retry** — the escalation keeps the escalator's `Idempotency-Key`, unique per escalator, so the same request again finds it and answers 201 with it and `Idempotent-Replayed: true`, staging nothing (R-37); the same key with another concern or reason is 422 `IDEMPOTENCY_KEY_REUSED`; two retries racing meet on the unique key and the loser replays; **(b) a second event** — a concern holds one OPEN escalation (409 `CONCERN_ESCALATION_OPEN`, and a partial unique index); **(c) redelivery** — the outbox's unique message key refuses a second message for the escalation, and WF-15 records one intent per source reference. A second escalation after the first is resolved is a new event with its own intent | Acceptance criterion 2; event-conventions EV-4, EV-6 |
| D-7 | **"Escalation routed through WF-11/WF-15".** WF-07's specification (ISS-GP-06) and WF-11's (APR-P-08, BR-APR-020) both say escalation is never approval, so an escalation is not a WF-11 run. WF-15 carries the escalation's notification (D-6) | Row; F-6 |

A concern's assignee is in the subject's `AssignedUserIds`, so an ASSIGNED grant reaches it (none ships, F-2) | Participation amendment |

## 3. The concern state machine

| From | To | Command | Permission | Waits for | Writes |
| --- | --- | --- | --- | --- | --- |
| — | OPEN | `POST /management-concerns` | `CONCERN_RAISE` (entities included) | the project APPROVED_PLANNED, ACTIVE or SUSPENDED | the concern; its impacts and computed severity, if any; the next review date |
| OPEN, ASSIGNED, IN_PROGRESS | (same) | `assess` | `CONCERN_MANAGE`, internal | a RISK_MATRIX version in force the impacts fit, mapping the overall level | the impacts replaced; severity recomputed and pinned |
| OPEN | ASSIGNED | `assign` | `CONCERN_MANAGE`, internal | an eligible assignee | the assignee |
| ASSIGNED, IN_PROGRESS | (same) | `assign` | as above | as above | the assignee |
| ASSIGNED | IN_PROGRESS | `start` | `CONCERN_MANAGE`, internal | — | — |
| IN_PROGRESS | PENDING_VALIDATION | `submit-resolution {resolution}` | `CONCERN_MANAGE`, internal | an APPROVAL_AUTHORITY route | the resolution; a WF-11 run for the revision |
| PENDING_VALIDATION | RESOLVED | WF-11 approves (edge 28) | WF-11's `APPROVAL_DECIDE` | the run approved | `resolved_at` |
| PENDING_VALIDATION | IN_PROGRESS | WF-11 returns, rejects or the run is withdrawn | as above | — | `revision_no` + 1 |
| OPEN … PENDING_VALIDATION | (same) | `review` | `CONCERN_MANAGE`, internal | a GOVERNANCE_PROFILE version | `next_review_date`, `last_reviewed_at` |
| RESOLVED | CLOSED | `close` | `CONCERN_MANAGE`, internal | no OPEN escalation | `closed_at` |

An escalation is OPEN → RESOLVED (`resolve {resolution}`, `CONCERN_ESCALATION_RESOLVE` through its role, internal) or OPEN → WITHDRAWN (`withdraw`, its escalator); it is raised on a concern OPEN to PENDING_VALIDATION and changes no concern's status. No other move exists, and the database refuses them.

## 4. Endpoints

All paths are under `/api/v1`, tag `ManagementConcern`, operation ids `ManagementConcern_*`. Every non-2xx answer is the R-23 envelope; every `POST` and `PUT` also answers 400 `IDEMPOTENCY_KEY_REQUIRED`/`…_INVALID`. Concern commands honour `If-Match` when sent (R-21) and answer 412 when it is stale.

## 5. Error codes

`ConcernErrorCodes` (R-27), beside the platform's `INVALID_TRANSITION` and `CONFIGURATION_MISSING`:

| Code | Status | When |
| --- | --- | --- |
| `CONCERN_PROJECT_NOT_ELIGIBLE` | 422 | Raising before approval or once COMPLETED; any change or escalation before approval or once CLOSED |
| `CONCERN_CATEGORY_INVALID` | 422 | The category is not a PUBLISHED CONCERN_CATEGORY item |
| `CONCERN_PRIORITY_INVALID` | 422 | The priority is not a PUBLISHED PRIORITY item |
| `CONCERN_IMPACT_INVALID` | 422 | The impacts do not fit the scale in force; every miss is a field issue |
| `CONCERN_ASSIGNEE_NOT_ELIGIBLE` | 422 | The assignee holds no role over the project now |
| `CONCERN_TARGET_DATE_INVALID` | 422 | A target resolution date before today, when set or changed |
| `CONCERN_CLOSED` | 409 | Any command on a CLOSED concern |
| `CONCERN_NOT_EDITABLE` | 409 | An edit, assessment or assignment once the resolution is with validation |
| `CONCERN_ESCALATION_OPEN` | 409 | A second escalation while one is OPEN, or a close while one is |
| `CONCERN_NOT_ESCALATABLE` | 409 | Escalating a RESOLVED or CLOSED concern |
| `CONCERN_ESCALATION_NOT_OPEN` | 409 | Resolving or withdrawing an escalation already ended |
| `IDEMPOTENCY_KEY_REUSED` | 422 | An escalator's key sent again with another concern or reason (R-37) |

## 6. How other modules build on it

1. **TASK-058** builds SCR-083–088 and MOD-036–039 on these 15 operations: severity is shown from `severityItemId` (labelled by FG-04's CONCERN_SEVERITY items), never edited; MOD-039 sends a reason only, and a retry must resend the same `Idempotency-Key`.
2. **Configuration**: an environment needs, before WF-07 works end to end, the CONCERN_SEVERITY items and the `CONCERN_SEVERITY_LEVEL_1…5` values in a published RISK_MATRIX version; WORKFLOW_POLICY `CONCERN_ESCALATION_ROLE`; APPROVAL_AUTHORITY `MANAGEMENT_CONCERN_RESOLUTION`; NOTIFICATION_ROUTING family `CONCERN_ESCALATION` with a published template for `ManagementConcern.ConcernEscalated` (F-3, F-5).
3. **WF-06**: materialisation now raises a real issue (D-10; `risk-management.md` change log).
4. **Dashboards and reports** read the register; the specification's controlled reporting projection is not built (F-1).
