## 2. Decisions

| # | Decision | Why |
| --- | --- | --- |
| D-1 | **One milestone, two owners (ICD-04).** The shared identity is `schedule.project_milestone`, one row per milestone, a WF-03 table in WF-03's module: its schedule representation and dates and its status. WF-05 has no milestone of its own: `milestone.milestone_achievement` names the row by `project_milestone_id`, a foreign key, and holds the claim, its evidence and the accepted Actual Achievement Date. The architecture test `MilestoneIdentityTests` fails the build if any type outside Schedule references `ProjectMilestone`/`BaselineMilestone` (the one foreign key configuration excepted) or any type outside Milestone references `MilestoneAchievement`, or if `Domain.Milestone` gains a type; `MilestoneSchemaTests` holds the schema to the ERD and the `milestone` schema to its one table | Acceptance criterion 1 |
| D-2 | **Edge 10, one direction: WF-05 → WF-03.** `IProjectMilestoneReader` (query) gives WF-05 a milestone's project, category, status and forecast date, authorizing no one, as `IScheduleActivityReader` does for edge 9. `IMilestoneAchievementRecorder` (command) lets WF-05, on acceptance, have WF-03 record the milestone ACHIEVED: WF-03 sets its own status, under its schedule lock, staged in WF-05's unit of work, so the acceptance and the status commit together or not at all (M-11). The accepted date is not passed: it stays WF-05's. WF-03 does not read WF-05, so there is no cycle (M-9). The ERD's "ACHIEVED is set by WF-03 on the WF-05 acceptance event" is met by this command rather than an outbox event, which would have needed the reverse reference and left a window in which a milestone is accepted but not ACHIEVED. §8.2 and `ModuleRegistry` record the direction (F-1) | ADR-003 §8.2 edge 10, "the direction TASK-050 implements is added by revising §8.2 first" |
| D-3 | **Edge 37: Milestone → Project (query).** `IProjectFactsReader` for the anchors every achievement operation is authorized on (M-7) and the lifecycle state a claim needs, as edges 1–6 and 36 give the other core modules. `ModuleRegistry` already allowed the reference for edge 35's event; §8.2 now lists the query (F-1) | M-7 |
| D-4 | **The revision model.** A revision is a row. Revisions of a milestone are numbered 1, 2, … (unique `(project_milestone_id, revision_no)`); the next claim — a first claim, a claim after a return, a correction of an accepted achievement — is the next revision, opened DRAFT by one command, `POST /milestone-achievements`. At most one revision of a milestone is open, DRAFT or SUBMITTED (409 `MILESTONE_ACHIEVEMENT_OPEN`, and a partial unique index, F-6). While a correction is open, the accepted revision stays current. When the correction is accepted, the old revision becomes SUPERSEDED with `superseded_by_achievement_id`, and keeps its claim, its accepted date and its review — every column but `status`, `superseded_by_achievement_id` and `updated_*` — while the new one becomes ACCEPTED: the previous row is saved first, because the ERD's partial unique index on ACCEPTED rows is checked row by row, and the dispatch commits both or neither | Acceptance criterion 2; the workbook's validation check |
| D-5 | **The workflow** (§3): DRAFT → SUBMITTED (submit), SUBMITTED → ACCEPTED or RETURNED (WF-11's outcome), ACCEPTED → SUPERSEDED (a later revision accepted). No edge leaves RETURNED or SUPERSEDED, none returns to DRAFT, and none edits an ACCEPTED revision. A DRAFT is edited (`PUT`, `If-Match`) and deleted (HARD_DRAFT, its evidence links ended); a SUBMITTED revision changes only by WF-11's outcome | The row's "Draft/Submitted/Returned/Accepted workflow" |
| D-6 | **The database holds the history** (migration `TASK-050_GuardMilestoneAchievement`). A revision is born DRAFT, after every earlier revision of its milestone; it moves only along the four edges; its claim changes only while DRAFT; an ACCEPTED revision changes only by being superseded by a later revision of the same milestone, and its accepted date is the date it claimed; RETURNED and SUPERSEDED are final; only a DRAFT is deleted; the table is never truncated. CHECK constraints tie the submitter, the reviewer, the accepted date, the successor and the return reason to the states that set them. The guard reads only the `milestone` schema (README R-7); that a revision's `project_id` is its milestone's is the service's to keep (F-6) | Acceptance criterion 2, for any writer |
| D-7 | **Acceptance through WF-11 (S-4, edge 25).** Submission starts a WF-11 run (`MilestoneApprovalRouting`: module `Milestone`, type `MilestoneAchievement`, routing key `MILESTONE_ACHIEVEMENT`, the ERD's APPROVAL_AUTHORITY subject type), staged with SUBMITTED. The requester is the claimant, so WF-11's own rule keeps them from accepting, and WF-11 gives no external user authority (`approval-framework.md` D-6). `MilestoneAchievementOutcomeHandler` applies the outcome in the dispatch transaction: APPROVED → ACCEPTED, the claimed date becoming `accepted_actual_achievement_date`, the final approver as reviewer; RETURNED, REJECTED and WITHDRAWN → RETURNED, with the deciding task's reason as `return_reason` (none for a withdrawal) and WF-11's decision on the audit event (F-4). An outcome for a revision no longer SUBMITTED, or for another revision, is audited as ignored (EV-5). An approval for a milestone cancelled in the schedule meanwhile is applied as a return (`MILESTONE_CANCELLED` on the audit event), because WF-03 cannot record it ACHIEVED | ERD E-4; S-4's consequence: "modules each build their own" is what the framework prevents |
| D-8 | **Evidence (edge 16, PTBC-006).** Evidence is linked to the revision, not the milestone, so each revision keeps its own and an accepted revision's evidence never changes. `POST …/evidence {documentId, documentVersionId, evidenceTypeItemId}` links the document (role ATTACHMENT) and pins the version, in one transaction: a version that is not CLEAN is 409 `DOCUMENT_NOT_AVAILABLE` and nothing stays linked. `…/withdraw` withdraws a piece. Both only on a DRAFT, and both touch the revision's row, so a submission that read the evidence before the change fails 412 rather than submitting evidence that is gone. Submission requires every evidence type EVIDENCE_POLICY makes mandatory for the milestone's category, in force now, to be satisfied as DocumentManagement decides it (`GetSatisfiedEvidenceTypesAsync`: VALID, active link, CLEAN): otherwise 422 `MILESTONE_EVIDENCE_REQUIRED`. With no EVIDENCE_POLICY version in force nothing is mandatory — PTBC-006's gate, "the backend enforces whatever policy is published" — and `GET …/evidence` returns `evidencePolicyVersionId: null` so the UI can label evidence optional pending policy; ambiguous versions fail closed (F-5) | PTBC-006; `document-management.md` §5 |
| D-9 | **`IApprovalRunReader`, new in Approval's contracts.** The outcome handler reads the run whose outcome it applies, for the deciding task's reason. `IApprovalRequests` could not serve it: `ApprovalRequestService` takes every `IApprovalOutcomeHandler` (it refuses to start a run no module can apply), so a handler depending on it is a dependency cycle the container rejects. The reader is the same query over the repository alone; `IApprovalRequests.FindBySubjectAsync` delegates to it. No behaviour of WF-11 changes, and no edge is added: reading a subject's runs is part of edges 25 and 28 | DRY; `approval-framework.md` D-2 |
| D-10 | **ADR-013 and two permissions.** `MILESTONE_VIEW` (Read) and `MILESTONE_SUBMIT` (Write: open, edit, delete, evidence, submit), group `MILESTONE`. R04 holds both at OWN: the project's owner anchor is its Project Manager, so OWN reaches exactly the projects the holder manages, internal or entity — the amendment's entity Project Manager submitting claims on their own project, and no other. Acceptance is not a milestone permission: it is WF-11's `APPROVAL_DECIDE`, internal only. Which other roles view or claim is Appendix A's (F-2). WF-03's milestone operations use `SCHEDULE_VIEW` and `SCHEDULE_EDIT`, as the rest of the schedule does | ADR-013's amendment to TASK-050 |
| D-11 | **WF-03's side** (`ProjectMilestoneService`). A milestone is created PLANNED in the project's schedule, with a PUBLISHED MILESTONE_CATEGORY item (422 `SCHEDULE_MILESTONE_CATEGORY_INVALID`) and, optionally, the live activity of the same schedule it completes (422 `SCHEDULE_MILESTONE_ACTIVITY_INVALID`). A PLANNED milestone is edited (`PUT`, `If-Match`) and cancelled; an ACHIEVED or CANCELLED one changes no more (409 `SCHEDULE_NOT_EDITABLE`, `INVALID_TRANSITION`), and none is deleted (RETAIN). Every write holds the schedule lock. While a baseline candidate is SUBMITTED to WF-11 no milestone is added, re-dated or cancelled (409 `SCHEDULE_NOT_EDITABLE`): `BaselineActivation` copies each live milestone's forecast date into `baseline_milestone` as the candidate activates, with its activities and dependencies. WF-05's acceptance is not a change to the plan and is not frozen. A milestone's detail carries the ACTIVE baseline's date for it and the forecast's variance from it, in days, positive = late | `schedule-baseline.md` F-7, §6 item 6 |
| D-12 | **What a claim needs.** The project ACTIVE (422 `MILESTONE_PROJECT_NOT_ACTIVE`), the milestone not CANCELLED (422 `MILESTONE_NOT_CLAIMABLE`, also for a milestone the caller cannot see, R-47), and a claimed date not after today, UTC (422 `MILESTONE_CLAIMED_DATE_INVALID`): an achievement is claimed once it has happened. An ACHIEVED milestone is claimable: that claim is a correction. Checked when opened, edited and submitted (F-7) | ERD; F-7 |
| D-13 | **Tables and migrations** (README R-7, one schema each): `TASK-050_CreateProjectMilestoneTables` and `TASK-050_AddProjectMilestoneCrossModuleForeignKeys` (`schedule`, with indexes I-35 and I-36), `TASK-050_CreateMilestoneAchievementTable` and `TASK-050_AddMilestoneAchievementCrossModuleForeignKeys` (`milestone`), `TASK-050_GuardProjectMilestone` (`schedule`) and `TASK-050_GuardMilestoneAchievement` (`milestone`). The columns, types, unique keys and foreign keys are the ERD's exactly (`MilestoneSchemaTests`) | ERD §5.6, §5.8 |
| D-14 | **API shape (R-2, R-3, R-4).** Collections are the ERD entities' plurals: `/project-milestones?projectId=`, `/milestone-achievements?projectMilestoneId=` or `?projectId=` (exactly one, 400 otherwise), newest first. A collection of a project the caller may not see is an empty page; a record they cannot see is 404, one they may see but not change 403 (R-47) | api-conventions |
| D-15 | **Every change is audited** in the saving transaction (event-conventions §4 rows 18 and 20): Schedule's `MilestoneCreated`, `MilestoneChanged` (title withheld) (DATA_CHANGE), `MilestoneCancelled`, `MilestoneAchieved` (LIFECYCLE_TRANSITION, with the accepted revision); Milestone's `AchievementStarted` (with the revision it corrects), `AchievementChanged` (narrative withheld), `AchievementDeleted`, `EvidenceAttached`, `EvidenceWithdrawn` (DATA_CHANGE), `AchievementSubmitted` (with the run and the EVIDENCE_POLICY version checked), `AchievementAccepted` (with the accepted date and the revision superseded), `AchievementReturned` (with WF-11's decision), `AchievementSuperseded`, `ApprovalOutcomeIgnored` (LIFECYCLE_TRANSITION, the last FAILED) | event-conventions EV-9 |

## 3. The achievement workflow

| From | To | Cause | Who | Writes |
| --- | --- | --- | --- | --- |
| — | DRAFT | `POST /milestone-achievements {projectMilestoneId, claimedAchievementDate, narrative}` | `MILESTONE_SUBMIT` on the project | the next revision number |
| DRAFT | SUBMITTED | `submit` | `MILESTONE_SUBMIT`; mandatory evidence held | the submitter; a WF-11 run |
| SUBMITTED | ACCEPTED | WF-11 APPROVED | WF-11's final approver, internal, not the claimant | the accepted date (the claimed one), the reviewer; the prior ACCEPTED revision SUPERSEDED; the milestone ACHIEVED in WF-03 |
| SUBMITTED | RETURNED | WF-11 RETURNED, REJECTED or WITHDRAWN; or APPROVED for a milestone cancelled meanwhile | the decider, or the requester who withdrew | the reviewer; the decision's reason |
| ACCEPTED | SUPERSEDED | a later revision ACCEPTED | as that acceptance | the successor |

## 5. Error codes

`MilestoneErrorCodes` (R-27), beside the platform's `INVALID_TRANSITION` and `CONFIGURATION_MISSING`:

| Code | Status | When |
| --- | --- | --- |
| `MILESTONE_PROJECT_NOT_ACTIVE` | 422 | A claim opened, edited, evidenced or submitted while the project is not ACTIVE |
| `MILESTONE_NOT_CLAIMABLE` | 422 | The milestone does not exist for the caller (`projectMilestoneId` NOT_FOUND) or is CANCELLED (NOT_ALLOWED) |
| `MILESTONE_CLAIMED_DATE_INVALID` | 422 | The claimed date is after today (UTC) |
| `MILESTONE_ACHIEVEMENT_OPEN` | 409 | The milestone has a DRAFT or SUBMITTED revision already |
| `MILESTONE_ACHIEVEMENT_NOT_EDITABLE` | 409 | An edit, deletion or evidence change of a revision that is not DRAFT |
| `MILESTONE_EVIDENCE_REQUIRED` | 422 | Submission without the evidence EVIDENCE_POLICY makes mandatory for the category (`evidence` REQUIRED; `GET …/evidence` names the types) |

Schedule's `ScheduleErrorCodes` gains `SCHEDULE_MILESTONE_CATEGORY_INVALID` and `SCHEDULE_MILESTONE_ACTIVITY_INVALID` (422).

## 6. How other modules build on it

1. **TASK-051** (SCR-046, SCR-062, the achievement screens and MOD-054): the milestone from `/project-milestones`, its revisions from `/milestone-achievements?projectMilestoneId=`, the current one by `isCurrent`; evidence through `…/evidence`; `evidencePolicyVersionId: null` is "optional pending policy" (PTBC-006). The review history is WF-11's `/approval-instances?subjectModule=Milestone&subjectType=MilestoneAchievement&subjectId=`.
2. **TASK-104** (ADR-014): an intake milestone recorded as achieved needs WF-03 to create its `project_milestone` row and WF-05 a revision with `project_intake_id`, reviewed like any other (F-8).
3. **Read side** (TASK-069/071): a milestone's Actual Achievement Date is its ACCEPTED revision's; a read projection from Milestone needs an edge 29 entry, which §8.2 does not list yet.
4. **AHDA**: the MILESTONE_ACHIEVEMENT route in APPROVAL_AUTHORITY (F-3), EVIDENCE_POLICY (PTBC-006, F-5), the MILESTONE_CATEGORY items, and the Appendix A grants (F-2).
