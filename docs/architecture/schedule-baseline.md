## 2. Decisions

| # | Decision | Why |
| --- | --- | --- |
| D-1 | **Module shape.** `Features/Schedule`: `Contracts` (`IScheduleService`, `IBaselineService`, `IScheduleHealthReader`, the DTOs and pages, `ScheduleErrorCodes`, `ScheduleApprovalRouting`, `Events`), `ScheduleService`, `BaselineService`, `BaselineWorkflow`, `BaselineActivation`, `ScheduleCalculation`, `DependencyGraph`, `WorkingDays`, `ScheduleVariance`, `ScheduleHealthRule`, `ScheduleHealthProjection`, `SchedulePolicy`, `ScheduleAccess`, `ScheduleAudit`, `ScheduleMapping`, `ScheduleDeclaredBaseline`, `BaselineActivationPrecondition`, `ScheduleHealthReader`, the repository port, the rebaseline-authorization port, and `EventHandlers/BaselineApprovalOutcomeHandler`. Entities in `Domain/Schedule`; repository and configurations in `Infrastructure/Persistence`. Schedule references Project's, Approval's, IdentityAccess's and MasterDataConfig's contracts (§8.2 edges 2, 21, E-U1, E-U2); A-1 to A-6 pass unchanged | ADR-003 §4.3 row 3, §6 |
| D-2 | **Tables.** ERD §5.6 without the milestone pair (F-7): `project_schedule`, `schedule_activity`, `schedule_dependency`, `project_baseline` (both baseline types, one discriminator), `baseline_activity`, `baseline_dependency`, `schedule_health_status`. Beyond the ERD (F-10): `schedule_activity.requested_start_date`, the planner's input the planned start is calculated from; `baseline_activity.parent_activity_id` and `activity_kind`, so a baseline's hierarchy and its ADR-009 leaves are reproducible from the copy alone; `schedule_health_status.health_rule_configuration_version_id`, the pinned rule (ERD D-13); `xmin` as the concurrency token of the schedule, activities, dependencies and baselines | The planned start is derived (DCL-SCH-03), so its input must be kept; a baseline is "fully reproducible" (ERD) |
| D-3 | **The backend calculates every date** (`ScheduleCalculation`, the spec's §11.3, §12.3), over the whole schedule after every change. A node with children is a SUMMARY, any other an ACTIVITY (leaf): the kind is derived, never sent. A leaf's planned start is the later of its requested start and each dependency constraint — FS: the working day after the predecessor's finish; SS: the predecessor's start; FF: no finish before the predecessor's finish — each moved by the lag, in topological order; its finish is the start plus its duration, day 1 being the start. A summary spans its live children. Cancelled nodes take no part. Every day is a working day until a calendar exists (F-3). A client never sends a planned or forecast date; one that does is ignored | Spec §2.3 "backend is authoritative" |
| D-4 | **Hierarchy and dependency rules, checked at save.** A parent is a live activity of the same schedule, never the node itself or a descendant (VAL-SCH-002/003, 422 `SCHEDULE_HIERARCHY_CIRCULAR`), and never a dependency end — it would become a summary, and a summary is none (BR-SCH-026, 422 `SCHEDULE_HIERARCHY_INVALID`). A dependency joins two distinct live leaves of one schedule (VAL-SCH-007), FS, SS or FF (F-11), with a lag of 0 or more working days (BR-SCH-025), and never closes a cycle (VAL-SCH-008, 422 `SCHEDULE_DEPENDENCY_CIRCULAR`). The cycle check runs after the schedule lock (D-8), so two requests that would each close half a cycle cannot both pass; the database refuses a cycle too, taking the same lock in its trigger, whoever writes. A dependency is never edited, only removed (HARD_WORKING) and added again. An activity is cancelled, never deleted (RETAIN), once it has no live children and no dependencies (409 `SCHEDULE_ACTIVITY_IN_USE`). A WBS code is unique in the schedule (409); it is a display code, not the activity's identity (SCH-CC-04) | The workbook's validation check: "a circular dependency between schedule activities is rejected at save time" |
| D-5 | **The Current Forecast is kept apart** (BR-SCH-002, BR-SCH-031). Until the project has an ACTIVE baseline a leaf's forecast follows its plan; from then on it is the planner's, set by `reforecast` on a live leaf (422 `SCHEDULE_ACTIVE_BASELINE_REQUIRED` before; 422 `SCHEDULE_FORECAST_INVALID` on a summary or cancelled node), and a change to the plan moves no forecast (BR-SCH-004). A leaf added after activation starts with its plan as forecast. A summary's forecast is always rolled up. The forecast is no part of a baseline, so it stays open while a candidate is with WF-11 | "Forecast deterioration is evidence of variance. It is not permission to move the Approved Baseline" (spec §1.1) |
| D-6 | **The baseline workflow** (§3), nine edges in `BaselineWorkflow`. An APPROVED candidate is born DRAFT from the working schedule, the project's next version number; a project has one candidate on its way at a time (409 `SCHEDULE_BASELINE_CANDIDATE_EXISTS`); a schedule with no live leaf has nothing to baseline (422 `SCHEDULE_BASELINE_EMPTY`). A DRAFT is deleted (HARD_DRAFT); its number is then free (F-17). ACTIVE is left only for SUPERSEDED; SUPERSEDED, REJECTED and WITHDRAWN are final. The spec's APPROVED_PENDING_ACTIVATION is not a state: the ERD has none, and activation runs inside the transaction that applies the approval, so an approval that cannot activate leaves the candidate SUBMITTED and its outcome waiting for redelivery (BR-SCH-030; F-8) | ERD §6 `project_baseline.status`; the spec's §5.2 |
| D-7 | **Approval is a WF-11 run started on submission** (`approval-framework.md` §5 step 1). `submit` moves DRAFT or RETURNED → SUBMITTED and calls `IApprovalRequests.StartAsync` in the same transaction: subject `Schedule`/`ProjectBaseline`/id/`revision_no`, routing key `SCHEDULE_BASELINE`, anchors the project and its department, routing input the governance profile. The requester is the submitter, so WF-11's own rule keeps the Project Manager from deciding their own baseline, and its authority rules keep externals from deciding at all (ADR-013). `BaselineApprovalOutcomeHandler` applies the outcome under the schedule lock, inside the dispatch transaction: APPROVED activates (D-8), RETURNED returns for revision + 1 under a new linked run, REJECTED and WITHDRAWN end it. An outcome applies only to the revision under review while SUBMITTED; any other is audited `ApprovalOutcomeIgnored` (EV-4, EV-5). Project starts its run when AHDA starts the review (`project-registration.md` D-3); a baseline has no AHDA review step outside WF-11's routing, so its run starts on submission and SUBMITTED means "with WF-11" | TASK-046 description "routing baseline approval through WF-11"; the spec's §3.1 |
| D-8 | **One ACTIVE baseline, superseded atomically.** Three layers. (1) The partial unique index `ix_project_baseline_active_project_id` (`project_id` WHERE `status = 'ACTIVE'`, ERD §5.6) refuses a second ACTIVE row for any writer and any interleaving. (2) Every write to a project's schedule and baselines — edits, submission, WF-11's outcome, the Declared Baseline — first locks the project's `project_schedule` row (`SELECT … FOR UPDATE`), so activations of one project run one after the other and each sees the last one's result. (3) `BaselineActivation` saves three times in one transaction: the ACTIVE baseline becomes SUPERSEDED, pointing at its successor; the working schedule's live activities and dependencies are copied into the candidate; the candidate becomes ACTIVE, its `activated_at` the predecessor's `superseded_at`. The order is forced: the unique index is checked row by row, and the database lets a copy be written only before its baseline activates and an APPROVED baseline activate only with one. Any failure rolls all three back; the prior baseline stays ACTIVE. While a candidate is SUBMITTED the plan it will activate from is frozen — every edit of activities and dependencies is 409 `SCHEDULE_NOT_EDITABLE`, and the database refuses them — so what activates is what WF-11 reviewed (SCH-CC-10). Every rebaseline after the first APPROVED baseline names an applicable WF-08 change authorisation at submission (BR-SCH-034, 422 `SCHEDULE_CHANGE_AUTHORIZATION_REQUIRED`; F-1); an approved candidate that was no rebaseline when submitted but meets an APPROVED baseline that activated since is returned, reason `REBASELINE_NOT_AUTHORIZED`, and the ACTIVE baseline stays | Acceptance criterion 1; api-conventions R-21 "invariants … are database constraints" |
| D-9 | **Variance and Schedule Health use the baseline's frozen copy as the reference.** `ScheduleVariance` measures the Current Forecast against the ACTIVE baseline's `baseline_activity` row — never the working plan, which keeps moving after approval, and never the forecast itself — in signed working days, positive late (BR-SCH-032, DCL-SCH-15): per activity on every read, and for the project (latest live-leaf forecast finish against `baseline_finish_date`) in `schedule_health_status`. No baseline entry, no variance: null, not 0. `ScheduleHealthRule` rates the project variance against `SCHEDULE_HEALTH_AMBER_FINISH_VARIANCE_DAYS` and `SCHEDULE_HEALTH_RED_FINISH_VARIANCE_DAYS` (WORKFLOW_POLICY, DURATION_DAYS, 0 < AMBER ≤ RED; TBC-SCH-003): GREEN, AMBER from the first, RED from the second — the spec's On Track, At Risk, Delayed. UNKNOWN without a variance or without thresholds; unlike WF-02's, missing thresholds do not refuse the command, because the health is recomputed by every schedule write and by WF-11's outcome, which must not fail for it. The live row is recomputed in the same transaction and audited when what a reader sees changes | Acceptance criterion 2; spec §9.16, §9.17, DCL-SCH-17 |
| D-10 | **ADR-015: approval follows the governance profile.** `submit` reads the profile's `requires_baseline_approval` (GOVERNANCE_PROFILE, `governance_profile_setting`): true for Standard and Full, a WF-11 run (D-7); false for Light, DRAFT or RETURNED → ACTIVE at once through the same `BaselineActivation`, audited `BaselineActivated` with `approval_required = false`. No settings published: 422 `CONFIGURATION_MISSING`. The switch, not the profile's code, decides, so AHDA's configuration stays the single source | ADR-015: "baseline approval is required for Standard and Full profiles only"; the ERD's column note "Light skips; Full cannot" |
| D-11 | **ADR-009's gate on Project's activation.** `IProjectActivationPrecondition` in Project's contracts: Project's `activate` calls every registered implementation after its own checks and before it writes, and references none of them. Schedule implements it (`BaselineActivationPrecondition`): met by an ACTIVE APPROVED baseline — approved through WF-11, or activated under ADR-015 — or by an ACTIVE Declared Baseline when the project has the ADR-014 intake marker; otherwise 422 `SCHEDULE_ACTIVE_BASELINE_REQUIRED`. A candidate under review is no baseline. The dependency stays Schedule → Project (§8.2 edge 2), as an outcome handler's stays source → Approval; a Project → Schedule query would close a cycle with edge 2. The check is the application's alone (F-9). WF-03 reports readiness and Project owns the transition (DCL-SCH-22) | Gate decision; TBC-SCH-009, which the gate decision closes |
| D-12 | **Two permissions; only R04's grants ship.** `SCHEDULE_VIEW` (Read) and `SCHEDULE_EDIT` (Write: initialize, activities, dependencies, forecast, candidates, submission), group `SCHEDULE`. R04 holds both at OWN: the spec's §3 makes the Project Manager the schedule's owner, and a project's owner anchor is its Project Manager, so OWN reaches exactly the projects the holder manages, internal or entity (R04 is employer-neutral, ADR-013). Baseline approval is WF-11's `APPROVAL_DECIDE`, not a schedule permission. The other roles' schedule grants wait for Appendix A (F-2) | Only source-backed grants ship (`authorization-engine.md` D-9) |
| D-13 | **ADR-014's Declared Baseline.** `ScheduleDeclaredBaseline.RecordAsync` writes the intake's baseline born ACTIVE: type DECLARED, `project_intake_id`, `declared_end_date` as its finish, `declared_scope`, no activities ("registered without a retrospective plan", ERD §5.6). Once per intake (unique key); a redelivered event changes nothing. It refuses a project that was not taken in on that date, or already has an ACTIVE baseline. The project's first APPROVED baseline supersedes it with no change authorisation: it is the first approved plan, not a rebaseline. TASK-104's `ProjectIntakeRecorded` consumer calls it (§8.2 edge 35; F-6) | ADR-014: "first-class baseline type distinguishable from an Approved Baseline" |
| D-14 | **The database holds the rules** (migration `TASK-046_GuardScheduleHistory`). A baseline is born DRAFT, or ACTIVE as a Declared Baseline; moves only along the nine edges; activates, if APPROVED, only with its copy; once ACTIVE changes only by being superseded by another baseline of its project; SUPERSEDED, REJECTED and WITHDRAWN never change; its project, type, version and intake never change; its revision moves by one when, and only when, a RETURNED candidate is resubmitted; only a DRAFT is deleted; the table is never truncated. A baseline's copy is written only while its APPROVED baseline is not yet ACTIVE, copies only its own project's activities, and is never updated, deleted or truncated. Activities and dependencies are frozen while a candidate is SUBMITTED. A dependency joins one schedule's activities and closes no cycle (checked under the schedule lock); it is never updated. Schedules, activities and health rows are never deleted and never move; a cancelled activity changes no more; an activity's status moves only PLANNED → CANCELLED until WF-04 adds its edges | Acceptance criterion 1, for any writer |
| D-15 | **API shape (R-2, R-3, R-28).** Collections are the ERD entities' plurals with the project as a filter: `/project-schedules`, `/schedule-activities`, `/schedule-dependencies`, `/project-baselines`, `/schedule-health-statuses`, each offset-paged; a baseline's frozen copy is two child collections of its aggregate root (`/project-baselines/{id}/baseline-activities`, `…/baseline-dependencies`). `projectId` is required. A collection of a project the caller cannot see is an empty page (the engine's `EvaluateAsync`, which records nothing); an item they cannot see is 404, one they may see but not change 403 (R-47). An activity's representation carries its planned dates, its forecast and the ACTIVE baseline's dates with the variance, side by side (BR-SCH-002) | api-conventions |
| D-16 | **Every change is audited** in the saving transaction (event-conventions §4 row 18): `ScheduleInitialized`, `ActivityCreated`, `ActivityChanged` (name withheld), `ActivityReforecast`, `DependencyCreated`, `DependencyDeleted`, `BaselineCreated`, `BaselineDeleted`, `DeclaredBaselineRecorded`, `ScheduleHealthRecomputed` (DATA_CHANGE; a recalculation's moved-activity count on the change that caused it); `ActivityCancelled`, `BaselineSubmitted` (with the run), `BaselineActivated` (with the baseline it superseded and whether WF-11 approved it), `BaselineSuperseded`, `BaselineReturned`, `BaselineRejected`, `BaselineWithdrawn` (LIFECYCLE_TRANSITION); `ApprovalOutcomeIgnored` (FAILED) | event-conventions EV-9; SCH-CC-20 |
| D-17 | **The read side reads what WF-03 stored.** `IScheduleHealthReader` (edge 29) returns the live Schedule Health row as stored. `ScheduleHealthOwnershipTests` (architecture) fails the build if any type outside the Schedule module and its own persistence references `ScheduleHealthRule`, its thresholds, `ScheduleVariance` or `ScheduleHealthStatus` | M-12; BR-SCH-010 "not independently recalculated by WF-02" |

## 3. The baseline workflow

| From | To | Cause | Who | Writes |
| --- | --- | --- | --- | --- |
| — | DRAFT | `POST /project-baselines {projectId}` | `SCHEDULE_EDIT` on the project | the next version, the plan's finish |
| — | ACTIVE | `ScheduleDeclaredBaseline` (ADR-014) | TASK-104's consumer | the Declared Baseline |
| DRAFT, RETURNED | SUBMITTED | `submit`, profile requires approval | `SCHEDULE_EDIT` | the WF-11 run; revision + 1 from RETURNED; the plan frozen |
| DRAFT, RETURNED | ACTIVE | `submit`, profile requires none (ADR-015) | `SCHEDULE_EDIT` | as the activation below |
| SUBMITTED | ACTIVE | WF-11 APPROVED | the run's last approver | the prior ACTIVE → SUPERSEDED; the copy; `activated_at` |
| SUBMITTED | RETURNED | WF-11 RETURNED; or APPROVED with no authorisation over an APPROVED baseline | the returner | — |
| SUBMITTED | REJECTED, WITHDRAWN | WF-11 REJECTED; the requester withdrew | the decider | — |
| ACTIVE | SUPERSEDED | another baseline activated | as that activation | `superseded_at`, `superseded_by_baseline_id` |

## 5. Error codes

`ScheduleErrorCodes` (R-27); the spec's §7.5 names in brackets:

| Code | Status | When |
| --- | --- | --- |
| `SCHEDULE_PROJECT_NOT_ELIGIBLE` | 422 | A write while the project is not APPROVED_PLANNED or ACTIVE |
| `SCHEDULE_NOT_INITIALIZED` | 422 | The project has no schedule |
| `SCHEDULE_EXISTS` | 409 | The schedule is initialized twice |
| `SCHEDULE_NOT_EDITABLE` | 409 | A candidate is SUBMITTED, or the activity is cancelled [SCHEDULE_NOT_EDITABLE] |
| `SCHEDULE_WBS_CODE_EXISTS` | 409 | Another activity has the WBS code |
| `SCHEDULE_HIERARCHY_INVALID` | 422 | The parent is not a live activity of the schedule, or is a dependency end [INVALID_HIERARCHY] |
| `SCHEDULE_HIERARCHY_CIRCULAR` | 422 | The move would make an activity its own ancestor [CIRCULAR_HIERARCHY] |
| `SCHEDULE_ACTIVITY_IN_USE` | 409 | A cancellation while live children or dependencies hang on the activity |
| `SCHEDULE_FORECAST_INVALID` | 422 | A forecast on a summary or a cancelled activity |
| `SCHEDULE_DEPENDENCY_INVALID` | 422 | Ends not two distinct live leaves of one schedule [INVALID_DEPENDENCY] |
| `SCHEDULE_DEPENDENCY_CIRCULAR` | 422 | The dependency would close a cycle [CIRCULAR_DEPENDENCY] |
| `SCHEDULE_DEPENDENCY_EXISTS` | 409 | The two activities are already linked that way |

## 6. How other modules build on it

1. **WF-08's change authorisation** (TASK-060, §8.2 edge 11): implement `IRebaselineAuthorization` against ChangeRequest's contract, or replace `NoRebaselineAuthorization`; add `fk_project_baseline_change_authorization_change_authorization_id` once `change_request.change_authorization` exists, and record `applied_at` there when the rebaseline activates (F-1).
2. **The intake path** (TASK-104) calls `ScheduleDeclaredBaseline.RecordAsync` from Schedule's consumer of `ProjectIntakeRecorded` (F-6).
3. **WF-04 execution** (TASK-048, §8.2 edge 9): a task references a schedule activity by id; actual dates and the IN_PROGRESS/COMPLETED states reach `schedule_activity` through a Schedule command, with an edge in `guard_schedule_activity()` for each new status move.
4. **WF-02 inputs** (`progress-update.md` F-1): once §8.2 gives Progress an edge to Schedule, `IProgressInputs` reads the ACTIVE baseline's copy (its leaves, dates and durations) and `IScheduleHealthReader`.
5. **The read side** (TASK-069 FG-01) renders `IScheduleHealthReader`'s value and never recalculates it; `ScheduleHealthOwnershipTests` holds it to that.
6. **Milestones** (TASK-050): `project_milestone` and `baseline_milestone` join the schema; a baseline's copy then includes milestone dates (F-7).
7. **AHDA's configuration**: a `SCHEDULE_BASELINE` route in APPROVAL_AUTHORITY, each profile's `requires_baseline_approval` (GOVERNANCE_PROFILE), and the two Schedule Health thresholds (WORKFLOW_POLICY), through FG-04 (F-4).
