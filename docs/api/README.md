## 2. Decisions

| # | Decision |
| --- | --- |
| **D-1** | **The API writes its own document.** `dotnet PMPlatform.Api.dll openapi <file>` (beside `migrate` and `seed`) asks the API's `IOpenApiDocumentProvider` for the v1 document after every endpoint is mapped, drops `servers` and writes it in the snapshot's form. It needs no database and no running server, takes about two seconds, and its output is byte-identical to what `/openapi/v1.json` serves and what the contract tests write under `UPDATE_OPENAPI_SNAPSHOT=1` (verified: `cmp` equal on `dev`'s snapshot before any change here). Alternatives not taken: fetching `/openapi/v1.json` from a started API, which needs PostgreSQL and the directory in the job; build-time generation (`Microsoft.Extensions.ApiDescription.Server`), which runs the entry point outside the API's own command handling. |
| **D-2** | **One job generates, guards and publishes.** `api-documentation` in `ci-quality-gates.yml` builds the API, runs `.github/scripts/openapi-publish.sh` and uploads `artifacts/api/` as `openapi-v1`. Because `ci-cd-pipeline.yml` calls that workflow as its `quality-gates` stage on every push to `main`, the same job is the "CI artifact on every merge to main"; on a PR it is the guard. Kept 90 days from `main` and `dev`, 7 from a PR. It is a required check (`protected-branches.ruleset.json`). |
| **D-3** | **The snapshot must equal the generated document, all of it.** The contract tests compare the snapshot one module (tag) at a time, and no contract test covers five of the 21 modules — IdentityAccess, MasterDataConfig, Notifications, Approval and DocumentManagement (126 operations) — so the snapshot could drift there unseen. `openapi-publish.sh` fails on any byte of difference and prints the diff and the command that rewrites it. The lint runs too, as a report (`contract-check.txt`), not a gate: its open findings are the contract tests' to judge. |
| **D-4** | **Swagger UI, from the API, under its own policy.** `Swashbuckle.AspNetCore.SwaggerUI` 10.3.0 serves swagger-ui 5.33.1's own files from the API at `/api-docs`; nothing is loaded from another origin. The API's `default-src 'none'` would block the page, so `SecurityHeaders` gives `/api-docs` alone `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'` — no `unsafe-inline`, no `unsafe-eval`, still never framed — and every other header unchanged. "Try it out" is off (`supportedSubmitMethods: []`) and the validator badge is off, so the page sends nothing but the request for the document. |
| **D-5** | **Modules start closed.** With every module's section open, swagger-ui stops rendering this 417-operation document after about ten operations: no error, the rest of the page never appears, with or without the CSP (§6.3). With `docExpansion: none` the page lists the 21 modules (R-51's tags) and each one opened renders in full. |
| **D-6** | **The session operations describe their bodies.** `SessionsController` returned `IActionResult` with no `[ProducesResponseType]`, so the document gave its 11 operations a bare `200` and no schema — and sign-in actually answers `201`. They now declare their bodies as every other controller does: a sign-in `201 SessionDetail` and `200 MfaPendingDetail`, the challenges `MfaChallengeDetail`, refresh and step-up `200 SessionDetail`, and so on. Additive only: 9 schemas and the 201s added, nothing removed or changed (R-10). |
| **D-7** | **DEV and SIT only, anonymous.** The acceptance criterion names DEV and SIT. `api_documentation` (platform variable, default false) becomes `ApiDocumentation__Enabled=true` on the Cloud Run service; `platform/guards.tf` refuses it for UAT and PROD at plan time, and `appsettings.json` defaults it off. The document and the UI are anonymous: the document is the committed snapshot of a public repository, so serving it discloses nothing the source does not, and a login wall would put the docs behind the MFA that R01 needs. Development keeps serving `/openapi/v1.json` (the contract tests read it); the UI there is the compose stack's choice (`ApiDocumentation__Enabled: "true"`). |

## 5. The published-spec audit

### 5.1 Procedure

`spec-audit.py` is the "manual audit" of the acceptance criterion made repeatable (api-conventions §9 row 12). For each endpoint in `spec-audit-sample.json` it checks, against a running environment:

| | Check |
| --- | --- |
| **D** definition | The environment's own `/openapi/v1.json` defines the operation, and every schema it reaches, exactly as the published document does |
| **Q** request | The body the audit sends conforms to the published request schema, and the API accepts it |
| **R** response | The status is one the published document lists, and the body conforms to the schema published for it: JSON types, nullability, enums, required properties, patterns, `uuid`/`date`/`date-time` formats, and no undocumented property |

The sample is eight endpoints of seven modules: sign-in (request body, 201 object), the current session, four paged collections (Dashboards, Project, Notifications, Reports) and the audit trail (AuditActivity), and one write with a body (IntegrationMonitoring's client error report). It writes nothing an environment keeps but the sign-in, its audit event and one labelled client error report. `GET /projects` needs a role that may list projects (R04 or R08 locally).

To run it against DEV once it exists, with the document from the `main` build DEV was deployed from:

```sh
gh run download <ci-cd-pipeline run id> -n openapi-v1 -D artifacts/api-audit/published
AUDIT_USERNAME=<an R04 test account> AUDIT_PASSWORD=… python3 docs/api/spec-audit.py \
  --base-url https://<DEV host> --spec artifacts/api-audit/published/openapi.v1.json --out artifacts/api-audit/dev-<date>.json
```

It passes when at least five endpoints were audited and every one matches; record the table in §5.3.

### 5.2 Rehearsal against the release image (2026-10-24)

DEV does not exist, so the audit ran against the closest thing: the release image built from this branch (`infra/docker/api.Dockerfile`, tagged `ahda-api:task-094`) on a scratch database migrated and seeded by that image, run as a deployed environment runs it — `ASPNETCORE_ENVIRONMENT=Staging`, so the secret store is required (the stand-in `infra/secrets/stub-store.py`) and the document and the UI are served only because `ApiDocumentation__Enabled=true`. The published document was `openapi-publish.sh`'s output for the same commit. Signed in as `local.r04`.

- The 21 module sections are listed; opened one at a time they render 52, 10, 15, 11, 8, 14, 16, 31, 15, 30, 12, 13, 22, 46, 9, 20, 11, 25, 11, 24 and 22 operations — 417, the document's count for each module.
